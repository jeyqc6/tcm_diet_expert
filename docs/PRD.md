## 1. 概述

一个中西医结合的个人饮食 agent。系统根据用户的中医体质、当前实时气候、近期饮食记录与在服补剂,由中枢 agent 派发中医食疗与现代营养学两个 SubAgent 分头推理,经独立调和层处理两套体系的分歧,再经核查 pass 验证溯源与安全性后输出饮食建议。

核心差异化:**主动调和两套体系的冲突,而非并列展示**。

**定位声明**:本项目是工程演示,不是医疗产品。不提供诊断、治疗或专业医疗建议的替代。

### 1.1 成功标准

| # | 标准 |
|---|---|
| 1 | 冲突调和正确率 ≥ 60%,且显著高于单 agent baseline |
| 2 | 引用溯源正确率 ≥ 85%,每条建议可追溯至原文 |
| 3 | 关键事实(过敏原/禁忌)落库率 ≥ 95%,落库后调用正确率 ≥ 99% |
| 4 | `docker compose up` 一键启动,新用户 10 分钟内可运行 |
| 5 | 完整的评估报告,含三档阈值对照与 baseline 对比 |

## 2. 问题与用户

### 2.1 目标用户

关注中医食养、同时坚持营养均衡的个人。V1 服务单一用户(作者本人),不做多租户。

### 2.2 问题陈述

用户希望通过饮食调理身体,但现有信息渠道存在结构性缺口:

| 现有渠道 | 缺口 |
|---|---|
| 搜索引擎 / 社交平台 | 只给单食材功效,不给整餐组合;信息真伪混杂 |
| 通用 AI 助手 | 无跨会话记忆,建议重复;不接实时气候;无溯源 |
| 饮食记录类 app | 只做热量记录,不理解中医食性 |
| 亲友经验 | 有中医直觉但缺营养学视角,且不掌握用户补剂情况 |

用户真正需要回答的问题形如:"在我这周已经吃了三顿羊肉、本周倒春寒、我在服鱼油的前提下,今晚该吃什么。"该问题的约束条件是**用户状态**,而非文档关键词。

### 2.3 问题特征

| 维度 | 评估 |
|---|---|
| 频率 | 每周约 3 次主动的调理性饮食决策 |
| 严重度 | 中低。不造成急性损失,但连续性中断即归零 |
| 广度 | 关注人群基数大,但 V1 明确只服务单用户 |
| 现状成本 | 单次决策需 15-30 分钟检索与拼凑,多数情况下放弃 |

## 3. 技术形态论证

本节回答两个**不同**的问题。混为一谈是常见错误——前者论证的是模型选择,后者论证的是控制流形态。

### 3.1 为什么需要 LLM 而非规则引擎

**组合状态空间过大。** 体质 9 类 × 气候状态约 8 种 × 近期饮食偏性约 5 档 × 补剂组合 × 目标标签,规则条目达 10⁴ 量级且存在优先级冲突(体质要求温补 vs 气候突然转热)。规则表写不完,更写不对。规则引擎适合作为 guardrail 硬边界,不适合作为推理主体。

**约束条件是用户状态而非文档关键词。** 用户真正的问题是"在我这周已吃三顿羊肉、本周倒春寒、我在服鱼油的前提下今晚吃什么"。这个查询无法用关键词表达,检索只能作为工具层的一环。

**需要跨会话状态。** 建议依赖近期饮食记录与长期趋势,需要持久化读写。

> ⚠️ 以上三条论证的是**"需要 LLM + 数据库"**,不是"需要 agent"。一个带数据库的 workflow 同样满足。不要用这三条回答"为什么不是 workflow"。

### 3.2 为什么不全是 workflow

**诚实的结论:本系统的主链路是 workflow,这是刻意的设计选择。**

按 Anthropic《Building Effective Agents》的定义——workflow 是 LLM 与工具通过预定义代码路径编排,agent 是 LLM 动态决定自身流程。对照本系统:

| 环节 | 形态 |
|---|---|
| 分级路由 | routing pattern —— workflow |
| 双 SubAgent 并行 | parallelization / sectioning —— workflow |
| 调和层 | aggregator —— workflow |
| 核查 pass | evaluator —— workflow |
| 菜品拆解 → 过敏原检查 | 确定性代码,不经过模型 |

**判据**:把链路画成流程图,若每个箭头的走向在编码时都能确定,它就是 workflow。本系统中只有五处不能确定:

| # | Agent 行为 | 不确定的是什么 |
|---|---|---|
| 1 | SubAgent 内部的工具调用决策 | 查几次天气、要不要追查某个食材。**含主动深挖**:从记忆中发现"连续三天同一主料"并自行判断是否值得提示 |
| 2 | 调和层的回补请求 | 依据不足时是否退回 SubAgent 补充查询 |
| 3 | 记录解析时的追问决策 | "晚上吃了点东西"要不要追问、追问什么 |
| 4 | 知识库未命中时是否外部检索 | ⏳ 未定,见 §17 开放问题 |
| 5 | 压缩时的重要性判断 | ⏳ 未定:固定阈值分层(workflow)还是模型判断(agent) |

**区分响应式与主动式**是关键。用户问什么答什么是 workflow;系统从状态中察觉异常并自行发起查询才是 agent 行为。第 1 项的主动深挖属于后者。

**为什么刻意保持主链路为 workflow**:固定的五段管线使每一段可挂独立指标(M3/M4/M5/M13/M14);自由规划的 agent 只能测最终输出,无法定位错误环节。**可评估性优先于自主性**——详见 `DECISIONS.md` D20。

## 4. 竞品与定位

| 现有方案 | 已解决 | 缺口 | 本项目差异 |
|---|---|---|---|
| Tongue Analyzer | 一次性体质评估,三框架并列 | 无持续记忆,不调和,不给整餐方案 | 持续记忆 + 主动调和 + 整餐输出 |
| TCM AID | 打卡 + 咨询预约 | 静态内容,非推理引擎 | 按状态动态生成 |
| Ayurveda AI 系列(7+ 款) | 验证"传统智慧 + AI"市场接受度 | 无 TCM 版本,单体系无需调和 | 填补空白 + 双体系调和 |
| B 端体质辨识设备 | 标准化测评 | 面向机构,一次性 | 面向个人的持续陪伴 |
| MyFitnessPal / Cronometer | 营养素追踪、热量管理 | 不理解中医食性,纯记录不建议 | 记录服务于推理;不在热量计算维度竞争 |
| 通用 AI 助手 | 通用推理能力 | 无结构化画像、无溯源、无 guardrail | 见 §8.4 baseline 对比 |

### 4.1 可防御性

| 组件 | 复制难度 |
|---|---|
| RAG 管线 | 极低 |
| 双 SubAgent 架构 | 低(稀缺的是论证与 ablation 数据,非架构本身) |
| 领域知识库整理 | 中 |
| **中西冲突调和规则表** | **高** |
| 分层记忆与关键事实保障 | 中高 |

### 4.2 价值主张

对关注中医食养、同时不愿放弃营养均衡的个人,中医与营养学的建议经常互相冲突,且没有工具记得用户最近吃了什么。本系统通过双专家推理与主动调和,输出带中西双理由与原文出处的饮食方案。区别于将两套说法并列呈现的现有产品,本系统直接给出调和后的结论。

## 5. 用户故事

1. 作为用户,我想用一句话记录今天吃了什么,以便记录成本低到可以坚持。
2. 作为用户,我想知道结合体质、当前气候与最近饮食该吃什么,以便调理具有连续性。
3. 作为用户,我想在中西医建议冲突时得到调和后的答案与理由,而非两套矛盾说法。
4. 作为用户,我想得到具体菜谱与购物清单,以便建议可直接执行。
5. 作为用户,我想知道食材搭配禁忌是否有依据,以便不被未证实说法误导。
6. 作为用户,我想问"我昨天/今天吃了什么",以便回顾自己的记录而不用自己回想。
7. 作为用户,我想针对我自己提出的具体候选(某道菜、几个可选项)问"这个能不能吃""该选哪个",以便获得针对已知选项的判断,而不必每次都从零生成一份新方案。
8. 作为首次使用的用户,我想被简单问几个问题就能开始用,而不是被迫先填完一整张表单;如果我不知道自己的中医体质,我想系统直接把体质测试的问题以对话形式问我,并告诉我结果是什么,而不需要我自己另外去做测评(见 `DECISIONS.md` D28)。

## 6. 范围

### 6.1 V1 能力清单

- 自然语言问答与多轮对话
- 文字饮食记录与结构化解析
- 体质问卷与用户画像(含目标标签、口味与情境偏好)
- 双库 RAG 检索(中医 / 营养学分离)与强制引用溯源
- 实时气候数据接入(Open-Meteo)
- 分级路由(记录 / 记录回顾 / 事实查询 / 候选评估 / 单领域 / 完整推荐,`DECISIONS.md` D25)
- 中医与营养学双 SubAgent 派发
- 独立调和层
- 输出核查 pass
- 跨会话记忆:用户画像持久化 + 饮食记录数据库查询 + 会话历史分层压缩
- Guardrails:输入防护、输出拦截、工具白名单、资源限额、ED 防护
- 全链路可观测(Langfuse)

### 6.2 Non-Goals

- 不提供疾病诊断性结论或治疗建议
- 不做精确的分量、克数、热量估算
- 不做减脂计划:不计算热量缺口、不设体重目标、不做体重轨迹追踪、不输出限制性表述
- 不做常驻式多 agent 编排(定义见 `DECISIONS.md` D1)
- 不做视觉识别(舌象、食物照片)
- 不做用户认证、多租户、移动端
- 不做长期趋势可视化看板
- 不做社交、分享、社区功能
- 不做采购下单集成
- 不接入地图/餐馆点评类外部数据:用户报出候选餐馆或菜名(如"楼下的黄焖鸡、米线")时,系统按该类菜式的一般营养/食性属性给出判断,不验证候选是否真实存在、不做具体商户推荐或比价(`DECISIONS.md` D25)
- 不做基于活动量的运动/生活方式推理(`DECISIONS.md` D17 已排除;用户在对话中提及的运动习惯作为自由文本被 SubAgent 感知,不作为独立的结构化输入维度)

### 6.3 目标标签体系

用户目标以定性标签进入推理,不引入数值目标。

| 标签 | 含义 | 消费方 |
|---|---|---|
| `improve_energy` | 提升精力、抗疲劳 | 中医(气虚/阳虚路径)+ 营养(B 族/铁) |
| `balanced_nutrition` | 营养均衡(默认开启) | 营养学 SubAgent |
| `weight_management` | 体重与代谢方向 | 中医(痰湿/湿热路径)+ 营养(控油、控精制糖、蛋白优先) |
| `digestive_comfort` | 肠胃舒适 | 中医(脾胃)+ 营养(纤维/发酵) |
| `sleep_quality` | 睡眠 | 中医(心肾)+ 营养(镁/色氨酸) |

`weight_management` 的边界:系统可输出"近期偏肥甘厚味,痰湿倾向明显,建议本周多用蒸煮、增加赤小豆薏米";不可输出任何热量额度、目标体重或减重速率。该边界由 §10 的 ED 防护规则强制执行。

#### 6.3.1 目标标签 vs 口味与情境偏好

`weight_management` 这类**目标标签**回答的是"我希望身体往哪个方向调理";而"不吃香菜""能吃辣""办公室没法热饭"这类**口味与情境偏好**回答的是"在满足调理方向的前提下,给我的方案要符合哪些约束"——两者不是同一件事,不应该合并进同一套字段(`DECISIONS.md` D25)。

持久性的口味/情境偏好(忌口、辣度耐受、长期性的用餐场景限制)进入用户画像的独立字段,由用户主动填写/确认后写入,不从对话中隐式推断——这一点与过敏原字段遵循同样的人在环原则(§10.2)。一次性的情境信息(比如某一次"今晚加班到很晚")不需要结构化字段,随对话原文进入 SubAgent 的任务上下文,由模型直接理解,不需要为每一种可能的场景都建一个字段。

### 6.4 后续版本

**V1.5**(有余量时):语音输入 · 菜谱与购物清单生成 · 冲突规则表扩至 50 条 · Prompt caching
**V2**(明确不做):分量热量估算 · 拍照识别 · 移动端 · 趋势看板 · 多用户

## 7. 系统概览

引擎层是一条五段流水线,后三段各自独立可评估。

```
交互层(Next.js,流式响应 + 溯源可展开)
      │
中枢 agent:分级路由 + 派发编排                          [M13 路由准确率]
      ├── 记录 ──────────────────────────┐
      ├── 记录回顾 ──────────────────────┤
      ├── 事实查询 ─────────────────────┤
      ├── 候选评估 ─┬─ 中医 SubAgent    │              [M3]
      │            └─ 营养学 SubAgent  │              [M4]
      ├── 单领域 ── 单 SubAgent ────────┤
      └── 完整推荐 ─┬─ 中医 SubAgent    │              [M3]
                    └─ 营养学 SubAgent  │              [M4]
                              │         │
                      调和层(独立调用,仅完整推荐/候选评估多候选时) │  [M5 调和正确率]
                              │         │
                      核查 pass ◄───────┘              [M14 拦截准确率]
                              │
                    调和建议 + 双理由 + 菜谱 + 购物清单
                    (候选评估分支:通过/不通过 + 理由,或候选间取舍)

工具层:中医检索 · 营养检索 · 天气查询 · 饮食记录查询 · 记忆写入 · 菜谱生成
记忆层:用户画像(常驻,含口味/情境偏好)· 趋势标签(常驻)· 饮食记录(数据库查询)· 会话历史(分层压缩)
观测层:Langfuse 全链路 trace
```

六条路由分支的完整定义、示例与判据见 §12.5 与 `DECISIONS.md` D25。

设计原则:每个模块都必须有对应的可测指标。

详见 `ARCHITECTURE.md`。

### 8.4 Baseline

| Baseline | 实现 | 证明 |

| B0 | BM25 关键词检索 + 模板 | 需要 LLM |

## 9. 幻觉容忍度

| 风险等级 | 场景 | 处理 |
|---|---|---|
| Critical(零容忍) | 特禀质过敏原;明确药食交互 | 硬阻断;无依据时必须声明不确定;宁可漏报不可误报 |
| High(极低容忍) | 具体症状对应建议;补剂叠加判断 | 强制降级为"传统食养参考,非诊断非治疗",提示咨询专业人士 |
| Medium(有界容忍) | 通用膳食方向;菜谱组合 | 需溯源;可输出低置信度结论但须标注 |
| Low(可接受) | 口味描述、烹饪步骤措辞 | 不额外约束 |

**推导出的硬约束**:任何食材推荐必须携带 `source_id`,无 source 的推荐不予输出。置信度不足时输出"依据不足,建议咨询专业人士"视为正确行为,评估中计为正确。

## 10. Guardrails

| 类型 | 规则 | 触发行为 |
|---|---|---|
| 输入防护 | 饮食记录字段中的指令性文本 | 剥离指令,保留食物实体,记录日志 |
| 输入防护 | 疾病或用药咨询意图 | 转入受限模式,仅通用信息 + 免责声明 |
| 输入防护 | 超长输入(> 2000 字) | 截断并提示 |
| 输出拦截 | 诊断性表述 | 正则 + 分类器双层拦截,替换为免责模板 |
| 输出拦截 | "多多益善"式表述 | 重生成,注入平衡约束 |
| 输出拦截 | 命中用户 `allergens` | 硬阻断,直接移除并说明 |
| 输出拦截 | 无 `source_id` 的推荐条目 | 移除 |
| ED 防护 | 数值化体重/热量表述 | 硬拦截,替换为定性表述 |
| ED 防护 | 极端限制性表述 | 拦截并重生成为温和版本 |
| ED 防护 | 用户索要热量或体重目标 | 说明不提供数值目标及原因,给出定性替代 |
| ED 防护 | 用户自述极低摄入或体重焦虑 | 停止限制性建议,提示寻求专业支持 |
| 相克断言 | 缺乏实证的民间说法 | 不确认为真亦不否定顾虑,说明证据状况 |
| 工具权限 | 白名单:检索、天气、记忆读写。无文件系统、shell、任意网络 | 越权调用拒绝并记录 |
| 资源限额 | 单会话 ≤ 15 次工具调用、≤ 80k token、≤ 60s | 强制收口,输出当前结论并说明未完成部分 |
| 循环防护 | 连续 3 轮无新增信息 | 终止派发,进入调和 |
| 隐私 | 健康数据本地存储,不进日志明文 | 上报前脱敏 |

### 10.1 核查 pass

调和层输出后、送达用户前的独立验证环节。非 agent:不做规划、不调工具、不多轮。

| 检查项 | 类型 | 不通过时 |
|---|---|---|
| 每条建议有 `source_id` 且指向真实 chunk | 确定性 | 移除条目 |
| 引用内容确实支持该建议 | LLM 判定 | 降级或移除 |
| 证据等级标注恰当(实证 / 传统经验 / 证据不足) | LLM 判定 | 补标注 |
| 过敏原交叉检查(含隐藏成分) | 确定性 + LLM | 硬阻断 |
| 补剂与药物交互无遗漏 | LLM 判定 | 退回调和层补充 |
| ED 防护规则 | 确定性 + 分类器 | 拦截或重生成 |
| 免责声明按需触发 | 确定性 | 补充 |

**核查 pass 只做拒绝,不做改写。** 生成与审查由同一模块承担会导致审查失效。核查 pass 在所有路由路径上均执行,不可跳过。

⚠️ **候选评估分支(`DECISIONS.md` D25)的核查 pass 判定标准需要单独一条**:该分支的输出是"结论(能/不能/选哪个)+ 理由",结论本身不是一条可挂 `source_id` 的独立建议条目;核查 pass 改为要求"结论必须能拆解出至少一条带 `source_id` 的支持理由",而不是要求结论字符串本身携带 `source_id`。规则细化见 `ARCHITECTURE.md` §6。

### 10.2 人在环检查点

| 检查点 | 触发 | 形式 |
|---|---|---|
| 体质确认 | 问卷完成,或用户自述体质 | 展示判定(可能含主 + 次体质,即"体质夹杂")与依据,用户确认或修改;自述路径同样需要确认展示,不直接采信(`DECISIONS.md` D28) |
| 过敏原录入 | 首次使用及每次新增 | 显式确认,不从对话隐式推断 |
| 口味与情境偏好录入 | 首次使用及每次新增 | 显式确认,不从对话隐式推断(与过敏原同一原则) |
| 低置信度建议 | 置信度低于阈值 | 标注 + 提供依据查看入口 |
| 冲突无规则命中 | 见 §11 | 说明分歧,选择权交回用户 |
| 长期画像写入 | 写入非日常记录字段 | 显式确认 |

### 10.3 OWASP LLM Top 10 对照

| 条目 | 暴露面 | 缓解 |
|---|---|---|
| LLM01 提示注入 | 饮食记录自由文本进入 SubAgent 上下文 | 输入过滤 + 系统提示声明数据非指令 |

| LLM05 供应链 | 知识库语料来源 | 见 §13.3 |

| LLM09 过度依赖 | 建议被当作医嘱 | 强制免责声明 + 溯源可查 |
| LLM10 无限消耗 | 派发爆炸 | 深度上限 2、调用上限 15 |

## 11. Fallback

| 失败场景 | 降级行为 | 用户提示 |
|---|---|---|
| 检索结果为空 | 静态"体质 → 通用调理方向"兜底表 | 说明未结合具体记录 |
| 检索相关度低于阈值 | 输出并标注低置信度 | 置信度标识 |
| 单个 SubAgent 失败 | 单边输出 | 说明仅从一侧分析 |
| 双 SubAgent 失败 | 降级为纯 RAG 问答 | 明确告知功能降级 |
| 冲突且无规则命中 | 说明分歧 + 保守交集建议 + 记录至 `conflict_gaps.jsonl` | 说明两套体系看法不一致 |
| 天气 API 失败 | 回退日历时令 | 静默,内部记录 |
| 语音识别置信度 < 0.7 | 回读确认 | 确认提示 |
| 输入模糊 | 追问一次,仍模糊则记为 `unspecified` | 单次追问 |
| 上下文超限 | 触发分层压缩;仍超限则丢弃最旧低价值记录 | 静默 |
| 模型 API 故障 | 切换备用模型 | 静默,记录切换事件 |
| 连续 3 轮无进展 | 强制收口 | 说明未解决部分 |

`conflict_gaps.jsonl` 中的条目构成下一版规则表的扩充素材与新增 eval case。

## 12. 非功能性需求

### 12.1 性能与可用性

| 属性 | 要求 |
|---|---|
| 并发 | 单用户,峰值 1 QPS |
| 可用性 | 无 SLA;外部依赖均有 fallback |
| 冷启动 | `docker compose up` 后 90s 内可用 |
| 知识库全量重建 | < 10 分钟 |

### 12.2 数据新鲜度

| 数据 | 要求 | 失效处理 |
|---|---|---|
| 实时气候 | ≤ 3 小时 | 回退日历时令 |
| 饮食记录 | 实时 | — |
| 中医知识库 | 静态,手动更新 | — |
| 营养数据 | 静态,季度检查 | — |
| 膳食指南 | 使用 RealFood.gov(2026-01 起替代 MyPlate) | — |

### 12.3 上下文预算

**中枢 agent,≤ 32k tokens**

| 分区 | 预算 |
|---|---|
| System prompt + 工具定义 | 2.5k |
| 用户画像(常驻,永不压缩) | 0.5k |
| 长期趋势标签(常驻) | 0.3k |
| 会话历史 | ≤ 10k |
| SubAgent 回传(各 ≤ 6k) | ≤ 12k |
| 输出预留 | 4k |

**SubAgent,≤ 24k tokens**:system prompt 1k · 任务上下文 2k(含用户原始提问文本,用于承接"加班到很晚"这类一次性情境信息,见 §6.3.1)· 检索结果 ≤ 12k · 内部推理累积 ≤ 6k · 输出 3k

**调和层,≤ 16k tokens**:system prompt 1k · 用户画像 0.5k · 两边结论与依据 ≤ 10k · 命中规则 ≤ 2k · 输出 2.5k
调和层不接收原始检索内容,仅接收两侧结论。

**核查 pass,≤ 12k tokens**:待核查建议全文 + 用户画像 + 被引用 chunk 原文。不含对话历史。

### 12.4 记忆访问模式

| 数据 | 访问方式 | 理由 |
|---|---|---|
| 用户画像(含口味/情境偏好) | 上下文常驻 | 体积小,每步推理均需 |
| 长期趋势标签 | 上下文常驻 | 体积小,用于主动发现偏移 |
| 饮食记录明细与聚合 | 工具查询 `query_diet_log(时间范围, 聚合维度)` | 数据持久化于数据库,查询优于携带 |
| 检索知识 | SubAgent 上下文 | 临时性 |

上下文压缩的作用对象为会话历史与检索结果,不含饮食记录。关键事实的保障机制为"落库前置":对话中出现的过敏、禁忌、补剂信息须在压缩发生前写入数据库,由 M6 度量。**该机制不局限于"记录"分支**——用户可能在任何分支的对话中提到关键事实(例如在请求完整推荐时顺带提到过敏原),须有一个跨分支的常驻检查步骤先于路由完成扫描,细节见 `ARCHITECTURE.md` §4.3。

### 12.5 分级路由

**六条分支**(`DECISIONS.md` D25:在原四条分支基础上,按真实使用场景走查后新增"记录回顾"与"候选评估"两条,理由与判据见 D25):

| 类型 | 示例 | 路径 | 目标延迟 | 目标成本 |
|---|---|---|---|---|
| **记录**(写入) | "晚上吃了番茄炒蛋" | 菜品拆解 → 过敏原即时检查 → **关键事实落库** → 人在环确认 | < 3s | ~$0.02 |
| **记录回顾**(查询) | "我昨天晚上吃了什么" | `query_diet_log` 单工具查询 + 轻量核查,不经过 SubAgent | < 3s | ~$0.01 |
| 事实查询 | "红枣是什么性味" | 检索 + 回答 + 核查 | < 4s | ~$0.02 |
| **候选评估** | "这个我现在能不能吃""黄焖鸡和米线选哪个" | 双派发(任务框架为"评估给定候选")+ 视候选数量决定是否经过调和层 + 核查(判定标准见 §10.1) | < 20s | ~$0.15 |
| 单领域 | "我最近缺什么营养" | 单派发 + 核查 | < 14s | ~$0.12 |
| 完整推荐 | "今天该吃什么" | 双派发 + 调和 + 核查 | < 35s | ~$0.33 |

调和层仅在双派发路径(完整推荐、以及候选评估中出现多候选需要取舍时)执行;核查 pass 在所有**查询**路径执行(记录分支除外,记录分支走的是过敏原即时检查而非核查 pass)。

**记录分支是写入链路,与其余五条性质不同**:

- 关键事实(过敏原/禁忌/补剂)必须在会话压缩发生**之前**落库,由 M6 度量
- 过敏原检查在此处即时执行一次,不等到输出阶段
- 该分支的路由准确率单独计入 M13——误判为查询会导致记录丢失,后果比其他误判严重

**记录回顾分支与事实查询分支的边界**:两者都是"检索 + 回答"的轻量路径,区别在检索目标——记录回顾查的是用户自己的 `diet_log`,事实查询查的是静态知识库 `knowledge_chunks`。合并成一条分支会让路由决策在两类问法之间失去可训练的边界,详见 `DECISIONS.md` D25。

## 13. 模型与数据需求

### 13.1 能力要求

| 角色 | 上下文 | 结构化输出 | 推理复杂度 | 关键约束 |
|---|---|---|---|---|
| 中枢 agent | ≥ 32k | 工具调用 + JSON | 高:路由 + 编排 | 强指令遵循;流式输出 |
| 中医 SubAgent | ≥ 24k | 必需 | 中高:多因素联合推理 | 中文语义理解强 |
| 营养学 SubAgent | ≥ 24k | 必需 | 中:结构化计算 + 交互检查 | 数值处理可靠 |
| 调和层 | ≥ 16k | 必需 | 高:跨领域仲裁 | 能在权威结论冲突时给出立场与理由,不折中回避 |
| 核查 pass | ≥ 12k | 结构化判定 | 低中:比对判定,不生成 | 低延迟低成本;判定稳定,倾向保守 |
| 输出分类器 | ≥ 4k | 二分类 | 低 | 低延迟(关键路径) |
| Embedding | — | — | — | 中文专业术语召回 |

本文档定义能力要求而非具体模型。选型结论记录于 `DECISIONS.md`。

### 13.2 模型策略

**双档策略。** 开发迭代期使用低成本模型档;正式跑分与交付在最终部署模型上执行。进入交付物的评估数字必须来自交付模型。

| 阶段 | 模型档 | 用途 |
|---|---|---|
| 迭代期 | 低成本档 | prompt 调试、冒烟集、手动测试 |
| 正式跑分 | 交付档 + 低成本档各一次 | 正式数字 + 跨模型对比 |
| 交付 | 交付档 | demo、文档标注 |

跨模型对比同时作为 prompt 健壮性检查:跨模型分数显著下降表明 prompt 过拟合于特定模型的指令遵循风格。

**替换触发条件**:某指标连续两次低于 Launch 阈值且 prompt 迭代无效;成本超预算 50%;供应商可用性事故。

**锁定风险缓解**:所有模型调用经由统一 adapter 层,业务代码不直接依赖厂商 SDK。该层须在骨架期建立。

## 14. 反馈与监控

### 14.1 隐式反馈

| 信号 | 测法 | 含义 |
|---|---|---|
| 次日饮食记录命中率 | 对比前日推荐与当日实际记录 | 建议是否被真正执行 |
| 追问率 | 收到建议后追问理由的比例 | 理由表述充分性 |

| 中断率 | 未读完建议即离开 | 输出长度与延迟 |

次日饮食记录构成上一次输出的天然验收数据,是本系统主要的效果信号。

### 14.2 显式反馈

每条建议提供正负反馈,负反馈可选原因标签:不合口味 / 无法执行 / 理由不认同 / 与体质不符。标记为"理由不认同"的样本直接进入 eval 集。

### 14.3 监控

| 项目 | 做法 |
|---|---|
| 全链路 trace | 分段记录路由决策、各阶段耗时与成本 |
| 成本监控 | 逐次记录 token 与估算成本,设日预算告警 |
| eval 回归 | 每次 prompt 或检索变更后运行冒烟集;任一指标跌破 Launch 阈值视为回归,须修复或回滚 |
| 模型漂移 | 每周固定运行冒烟集作为漂移探针 |
| 安全告警 | 输出拦截触发时记录高优日志 |

## 16. 伦理约束

| 议题 | 立场 | 落地 |
|---|---|---|
| 传统医学表述 | 保持其自身语境,不伪造科学依据抬高可信度 | 输出区分"中医理论认为"与"研究显示" |
| 传统医学评价 | 不以"迷信""安慰剂"框定,呈现事实,判断交由用户 | 中立措辞,双边溯源 |
| 健康焦虑 | 不放大无关紧要的差异,不暗示后果 | 仅在对当前用户重要时强调差异 |
| 饮食失调风险 | 最高优先级伦理约束 | 四条 ED 防护规则 + 核查 pass 确定性拦截 + 该切片指标要求 100% |

### 17.1 关于 web search 的未决冲突

知识库未命中时让 SubAgent 自行发起外部检索,会显著增强 §3.2 第 4 项的 agent 成分。但它与现有溯源体系存在**直接冲突**:

| 问题 | 说明 |
|---|---|
| 无 `source_status` | 核查 pass 第一条规则是"每条建议必须有 `source_id` 且指向真实 chunk"。搜索结果没有 |
| 无 `evidence_level` | 输出措辞强度依赖这个字段,搜来的内容无法定级 |
| M2 怎么算 | 引用溯源正确率的分母里要不要计入外部来源 |
| 工具白名单 | §10 明确写"无任意网络",引入需要修订 guardrail |

**决策前必须先回答**:外部检索结果是否单独标记为 `evidence_level: 外部未核实`,并在输出中显式区分。若做不到,不引入。

**沙盒 / 代码执行:明确不做。** 用户设想的"计算最近吃了几次饺子"用 SQL 即可;引入 shell 会大幅扩大攻击面而收益不明确。
