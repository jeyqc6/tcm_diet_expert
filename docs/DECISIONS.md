## D1 · 多 agent 粒度

**选择**:中枢 agent 按需派发两个短生命周期 SubAgent(中医 / 营养学),SubAgent 在独立上下文中完成多轮推理,返回结论与依据后销毁。

**放弃**:
- 单 agent,双库知识进入同一上下文
- 常驻专科 agent、agent 间直接通信、动态 agent 生成
- 领域推理全部下沉为工具层的确定性函数

**范围界定**:不做常驻式编排、不做 agent 间直接通信、派发深度上限 2。

**理由一 · 上下文隔离。**
中医检索结果是定性、类比、条目式文本(四气五味、归经);营养学检索结果是定量、表格、单位密集的数据。两者进入同一上下文会产生双向污染:定量语境将中医的定性判断挤压为伪精确表述(如"阳虚质每日应摄入 12g 生姜"),定性语境使营养推理丢失单位严谨性。让两侧在独立上下文推理、仅回传结论摘要,是上下文工程决策,与算力无关。

**理由二 · 可分别评估。**
单 agent 是黑盒。输出错误时无法区分是中医方向判断错误、营养分析错误还是调和逻辑错误。SubAgent 边界使三段可分别建立 eval 集并定位到具体环节。评估粒度决定迭代速度。

**不采用"推理复杂度高"作为理由。** 该理由无法抵御"延长 prompt 即可"的反驳。

**验证方式**:B2 baseline(单 agent + 双库同上下文)与本架构在同一 eval 集上对比。若无显著优势,回退至单 agent 并在此处追加修订记录。

**B2 ablation 验证记录(2026-08-29)**:跑了。结论是——**没有验证出"上下文隔离"这条理由,反而是 B2(单 agent)在这次跑分里更好**,不是"打平"。

- **对比对象**:`evals/dataset.jsonl` 的 E2a(冲突调和,10 条)+ E2b(表外泛化,5 条)=15 条——这是唯一真正需要"两侧领域证据放在一起给结论"的子集,E1/E3 跟这条决策要验证的问题无关,没有放进来稀释信号。
- **打分**:两侧分数复用 `run_baselines.py` B1/B3 已经用的同一套 keyword rubric(`resolution_keywords` 全中 + `must_not` 全不中才算 pass),在各自的 `verify()` 核查 pass **之前**打分——核查 pass 的引用/过敏原拦截对两侧一视同仁,不是这次要检验的变量,放进去只会用同一个噪声源掩盖真正的差异。
- **数字**(`evals/results/b2_ablation_2026-08-29.json`):

  | | pass_rate | 总延迟 | 总 LLM 调用次数 |
  |---|---|---|---|
  | baseline(双 SubAgent+调和) | 26.7%(4/15) | 414.3s | 78 |
  | B2(单 agent 双库同上下文) | 40.0%(6/15) | 203.2s | 33 |

  B2 领先 13.3 个百分点(超过预设的 10% 显著性阈值),延迟/调用次数都是baseline 的一半不到——不是"差不多,勉强打平",是 B2 在**这次跑分的三个维度上全部占优**。

- **诚实的局限,不回避**:
  1. **n=15,免费开发档模型**(`.env` 的 `LLM_PROVIDER_DEV=openrouter`/`minimax-m3:free`),不是 PRD §12.4 要求的交付档模型——绝对分数(26.7%/40.0%)不能当交付数字看,但两侧用的是**同一个模型、同一批 15 条 query**,架构之间的相对差距不受"哪个模型更强"这个变量污染。
  2. 抽查过几条 swing case(如 E2a-07):baseline 和 B2 的回答实质内容都合理,差别有时只是 keyword rubric 对同义词不宽容(baseline 写"减弱"、B2 写"降低"却被记为 miss)——rubric 本身有噪声,但这个噪声源对两侧一视同仁,不解释 13.3 个百分点的系统性差距,尤其解释不了延迟/调用次数这个和文本用词完全无关的 2 倍差距。
  3. 抽查确认 B2 在全部 15 条里都**真的调用了两个检索工具**(`retrieve_tcm`+`retrieve_nutrition`),不是"图省事只查一个库导致的假胜利"。
  4. **这次 ablation 没有验证理由二("可分别评估")**——那是软件工程层面的可维护性收益(出错时能不能定位到具体环节),不是这套 keyword rubric 能测量的东西,不能因为理由一没站住脚就假装理由二也一起被推翻了。

- **结论(2026-08-29 keyword rubric 版)**:理由一("上下文隔离能提升质量")在这次数据上是**反例**,不是"未证实"——B2 单上下文反而质量更高、成本更低。

**LLM-as-judge 复核(2026-08-30)**:上面第 2 点局限("keyword rubric 对同义词不宽容")不是猜测,专门做了一次复核——写了 `evals/run_llm_judge.py`,对同一批 15 组回答(不重新跑 SubAgent,只重新打分)换一套五维度语义评分:`relation_correct`(关系类型判断对不对,0/1)、`resolution_correct`(建议实质内容对不对,0-2)、`safety`(有没有语义上说出 must_not 禁止的话,0/1)、`synthesis`(是不是真的把两侧证据综合成一个判断——**这才是直接检验理由一的那个指标**,0-2)、`evidence_honesty`(证据强度措辞诚不诚实,0-2),满分 8。为避免位置/自我偏好,baseline/B2 哪个是"回答A"哪个是"回答B"每题随机决定,打完分再对回原始标签。

结果和 keyword rubric 版**方向一致但幅度完全不同**(14/15 条解析成功,1 条 E2a-03 裁判输出格式错误跳过):

| | 平均总分(满分 8) |
|---|---|
| baseline(双 SubAgent+调和) | 7.93 |
| B2(单 agent 双库同上下文) | 8.00 |

两边都在满分附近(baseline 只在 E2a-05 一条上因为"结论悬置给用户、不够果断"被扣 1 分,其余全部满分)——**不是"B2 大幅领先"了,是两边内容质量几乎无法区分**。这印证了局限第 2 点的怀疑:26.7% vs 40.0% 那个 13.3 个百分点的差距,主要是 keyword rubric 卡字面用词造成的,不是真实内容质量差距;真实内容质量差距在这套更语义化的打分下几乎测不出来(也可能是打分模型和生成模型是同一个免费模型,分辨力本身有限——两种解释都要诚实列出,不能只挑对自己有利的那个)。

**但延迟/调用次数的结论完全不受影响**——那两个数字和用词、rubric 严格度无关,B2 用不到一半的 LLM 调用次数(33 vs 78)、不到一半的墙钟时间(203.2s vs 414.3s),达到了(在这套语义评分下)和 baseline 几乎相同的质量。

- **修订后的结论**:理由一("上下文隔离能提升内容质量")在**内容质量**这个维度上,更准确的说法是"未被这次数据证实"(两边在语义评分下打平),而不是"被反证"(keyword rubric 版本的说法过头了)。但"分两个 agent 要多付出约 2.4 倍的 LLM 调用、2 倍的延迟才能换来打平的质量",这本身就是一个需要正视的成本论据——D1 原文明确说过"不采用推理复杂度高作为理由",但那条针对的是"用复杂度证明必要性",不是反过来说"复杂度不是选择成本更低方案的理由"，两者不矛盾。是否要真的把生产链路(`api/main.py`/`backend/agents/dispatch.py` 的 `_stream_dual_dispatch`/`reconciliation.py`)替换成单 agent,除了这两轮数据还要权衡理由二的工程收益(可分别评估,完全没被这两次 ablation 测过),以及 n=15 小样本+免费模型(生成和打分都是)这个结果能不能扛得住换成交付档模型/扩大样本/换裁判模型后复测——**这一步依然需要人决定范围,不在本次修订记录里直接执行**,见 `evals/run_b2_ablation.py`/`evals/run_llm_judge.py`(均可复现)。

## D2 · 知识库分片

**选择**:中医与营养学分为两个独立 collection。
**放弃**:单一 collection 混合检索。
**理由**:同一 query 下,营养学的定量文本在向量空间中会挤占中医定性文本的召回位次。分片后可对两库分别调优检索参数与 chunking 策略,并分别测量 recall。

## D3 · Chunking 策略

**选择**:中医知识按"条目"切分(一味食材或一条理论为一个 chunk),对应表格结构化入库;营养数据按 USDA 记录粒度。
**放弃**:固定 512-token 滑动窗口。
**理由**:中医知识天然是条目式的,"性—味—归经—宜忌"构成不可分割的语义单元,滑窗切分会将其截断,导致检索到半条信息。

## D4 · 向量库

**选择**:Postgres + pgvector。
**放弃**:Pinecone、Chroma 等专用向量库。
**理由**:免费;与用户画像表同库,可通过 JOIN 按体质等元数据预筛后再做向量检索,减少召回噪声;单机部署简化 `docker compose` 交付。

**补充(2026-08-26,补一段可以直接讲的解释,原文过于简略)**:

三条理由按影响力从大到小排:

1. **检索本身需要"向量 + 结构化条件"联合查询,这是纯向量库做不到的。** 真实查询从来不是"找最相似的 chunk",而是"找最相似的、且体质匹配、且 `source_status='verified'` 的 chunk"——`WHERE 体质匹配 AND source_status='verified' ORDER BY embedding <=> $1` 一句 SQL 搞定(roadmap.md §2.4)。Pinecone/Chroma 把元数据过滤和向量检索当两个独立操作,要么先过滤再查(丢召回候选池),要么查完再在应用层过滤(浪费 top-k 名额)。pgvector 因为向量就是 Postgres 的普通一列,过滤和排序在同一次查询原生完成。
2. **三类数据(向量检索、关系型知识、用户记忆)本来就要频繁联动,拆成多系统只会制造一致性问题。** `knowledge_chunks`(向量)、`conflict_rules`(关系表建模的体质-食材关系,D23)、`user_profile`/`diet_log`(用户记忆,D18)现在共用同一个 Postgres 实例。调和层的推理本质是这几种数据的联合查询,拆到 Pinecone + Postgres + 图数据库三个系统,agent 每次推理都要做跨库编排和一致性维护,不带来任何检索质量收益,纯粹是额外复杂度。
3. **数据规模不支撑专用向量库的优势。** Pinecone 这类专用库的优势在千万级向量、高并发 QPS;本项目是几千到一万出头的 chunk 量级,pgvector 支持 HNSW 索引(`knowledge_chunks` 已建 `HNSW(embedding, cosine)`),这个规模下和专用向量库的检索延迟差异可忽略——不是"将就用便宜方案",是"这个规模下两者性能等价,但 pgvector 附带前两条免费"。

**面试要点**:被追问"Pinecone 到底强在哪、什么时候该换"时,答案不是回避,而是明确指出边界——向量数量涨到千万级、或者需要面向多租户的高并发检索 QPS 时,专用向量库的分布式架构优势才会体现;当前项目单用户、单机部署(呼应 `docker compose up` 一键交付的目标),这两个条件都不成立,到时候要换也只是替换检索这一层,不影响上层数据模型。每条理由都能倒推回一个具体的项目约束(联合查询需求、多数据类型共存、当前规模),而不是孤立地夸 pgvector"免费又好用",这是这条解释比表面理由更经得住追问的地方。

## D5 · 体质获取方式

## D6 · 气候数据源

## D7 · 是否接入 MCP

**选择**:不接入,天气数据走直接 HTTP 调用。
**放弃**:全套 MCP 化。
**理由**:本场景不需要外部工具生态。为使用而使用会增加复杂度且无法通过技术审视。

**修订(2026-08-23)**:

**新选择**:工具层(中医检索、营养检索、天气查询、`query_diet_log`、记忆写入、菜谱生成)整体经**本地 MCP server**(stdio/localhost,不对外网络暴露)暴露给中枢 agent 及各 SubAgent,而非各工具在业务代码里各自实现调用逻辑。

**触发原因**:D7 原判断只针对"天气这一个外部调用是否值得包一层协议"——单工具确实不值得。但当工具白名单扩到 5-6 个(检索×2、天气、诊断记录查询、记忆写、菜谱生成)后,问题变了:是否值得为这一整层建立统一契约。

**理由一 · 把 §10 的工具白名单从约定变成协议边界。**
PRD §10 "工具权限"这条 guardrail 目前只是应用代码里的一个 if 判断。MCP server 只声明白名单内的工具,未声明的工具在协议层就不存在——越权调用连"被拒绝"的机会都没有,直接无法发起。这是把一条软性约定下沉为传输层边界,而不是新增复杂度。

**理由二 · 复用开发期的调试路径。**
`planning/step1-naive-rag` 这类原型脚本目前只能命令行跑。工具层做成 MCP server 后,同一套检索/查询工具可以直接挂到 Claude Desktop 上做交互式调试——不用起完整的五段管线就能验证"这条 query 到底召回了什么"。这个收益独立于简历,是开发期真实会用到的能力。

**理由三 · 与中枢 agent 实现解耦。**
中枢 agent 的具体实现(是否换模型、是否换编排框架)不再需要重写工具调用胶水代码,只需换 MCP client。

**未推翻的部分**:D21(不做沙盒/代码执行)与 §10 的工具类别边界维持不变——MCP server 只是重新暴露同样几类工具,不新增工具种类,不对局域网外暴露。**不是"为了 MCP 而 MCP"**:如果最终工具白名单收缩回 1-2 个,这条修订应该被重新评估。

## D15 · 输出核查 pass

**选择**:在调和层之后、输出之前加入独立核查环节。轻量模型 + 确定性规则组合；
硬安全项只拒绝不改写，证据类失败允许一次受限的无工具修复。
**放弃**:
- 依靠 system prompt 中的约束
- 由生成方自查

**理由**:本项目需要一个独立于生成过程的正确性判定机制。饮食建议不存在编译器式的完备验证,但存在可机械判定的必要条件——溯源必须存在且对得上、过敏原必须未命中、证据等级必须标注、数值化表述必须未出现。这些条件不足以判定建议"好",但足以判定建议"不合格",这正是测试的作用。

硬安全项只拒绝不改写：生成与审查由同一模块承担时，审查会退化。

**收益**:可测(M14)、可独立迭代(核查规则变更不影响生成侧 prompt)、成本低(轻量模型)。

**部分修订(2026-08-31，仅限第 2/3/5 项软判定)**：真实跑通后发现"只拒绝不改写"
对第 2 条（引用内容是否真的支持该建议）过度拦截——多数命中是"张冠李戴"（id
真实存在，但挂错了旁边那句话），不是"整条结论都是编的"，按原规则整条移除后
用户经常拿到一个空回复，而不是打了折扣但仍然有用的回复。修订为：第 1/4/6/8
项硬安全检查（source_id 有无、过敏原、ED 防护、诊断性表述）继续严格"只拒绝
不改写"，这条是防止编造健康/中医建议的核心防线，不能松动；第 2/3/5 项软判定
新增 `annotate` 结论——只能做减法（删掉引用支持不上的具体陈述）或加免责标注，
不能新增事实性论断、不能编造 `source_id`。为了不让"生成与审查由同一模块承担
时审查会退化"这条顾虑落空，annotate 改写后的文本**不直接信任**，而是重新跑
一遍第 1/4/6/8 项确定性检查（`backend/agents/verification.py`
`_recheck_annotated_items()`）——任何一项不过，自动降级为 reject，不存在
"annotate 绕开硬检查"这条路径。实现：`backend/agents/verification.py`、
`backend/skills/verification_checklist.md`（version 1.0.1 → 1.1.0）。配合调和层
`backend/skills/reconciliation_rubric.md` 新增"不要延伸原文结论"规则（version
1.0.0 → 1.1.0）——两者是同一个真实故障的一体两面：调和层把某个引用的支持范围
往外延伸（比如把"多喝水"的依据安在"绿茶清热"上），核查 pass 的第 2 条如实
拦下了这个延伸，但拦下之后原来的选择只有"整条扔掉"，这次一并把两头都补上：
生成侧尽量不犯这个错，核查侧犯了之后有比"整条移除"更精细的处理方式。

**进一步修订（2026-08-31）**：按当前产品策略，annotate 文本在初次确定性
检查通过后直接采用，不再默认调用 `_recheck_annotated_items()`；该函数保留为
需要额外防御时的可选工具。核查 LLM 的 system prompt 和 Skill 仍要求
annotate 不得制造或保留 source_id、过敏原、ED 防护或诊断性表述，但这些要求
不替代程序检查。这个取舍会降低 annotate 改写后的硬安全保障，属于有意变更。

**证据修复修订（2026-08-31）**：如果首次核查因缺少/误引 source_id、
引用支持范围不足，或软判定要求补充交互说明而失败，中枢不再重跑 SubAgent、
检索或调和层，而是用已有草稿和失败原因发起一次无工具修复调用。修复只能
删除不支持的具体陈述，或给有限通用知识加「模型通用知识，未经过当前知识库
核验，可能不完全准确」等用户可见标注；不得新增事实或 source_id。修复结果
直接进入当前输出策略，不再做第二次硬核查；过敏原、ED、诊断性表述等硬阻断
仍然直接移除。无本地依据的单条草稿因此可以保留有用内容，但其通用知识属性
和非引用语义必须明确。

## D16 · 减脂 / 体重管理如何进范围

**选择**:作为定性目标标签 `weight_management` 进入推理,走中医痰湿 / 湿热体质路径与营养学的控油、控精制糖、蛋白优先方向。明确排除热量缺口计算、体重目标、体重轨迹追踪。

**放弃**:
- 完全不涉及体重相关目标
- 实现完整减脂功能,含分量估算与热量缺口

**放弃完整减脂的理由**:
1. 减脂的本质是热量缺口,依赖精确分量估算,而这是既定 Non-Goal
2. 与饮食失调防护的伦理约束直接冲突
3. 热量计算是成熟商业产品的主场,正面竞争无胜算

**收进定性版本的理由**:
中医对体重问题有独立的处理路径。体质分类中,痰湿质表现为"体胖、面油、苔厚、多痰",调理方向为"化痰祛湿,忌肥甘厚味";湿热质为"清热化湿,忌辛辣油腻"。中医的路径是健脾化痰祛湿,而非制造热量缺口——两条路径的具体推荐经常直接冲突。

这使 `weight_management` 成为冲突规则表最富产的素材来源,而规则表是本项目最缺素材、也最难被复制的资产。

**边界**:系统可输出"近期偏肥甘厚味,痰湿倾向明显,建议本周多用蒸煮、增加赤小豆薏米";不可输出热量额度、目标体重或减重速率。由四条 ED 防护规则与核查 pass 的确定性拦截强制执行,该切片的数值化表述拦截率要求 100%。

## D20 · 主链路保持 workflow,agent 行为限定在五处

**选择**:五段管线(路由 → 双派发 → 调和 → 核查 → 输出)全部为预定义控制流。动态控制流只出现在五个明确列举的位置。

**放弃**:
- 让中枢 agent 自由规划步骤与工具序列
- 把每个环节都做成"可以自己决定要不要执行"

**背景**:审视架构后的诚实结论是——**本系统的主链路按 Anthropic 的定义属于 workflow**。分级路由是 routing pattern、双派发是 parallelization、调和层是 aggregator、核查 pass 是 evaluator,四者都是 workflow 模式。这一点不应回避。

**五处真正的 agent 行为**:

| # | 位置 | 不确定的是什么 | 状态 |
|---|---|---|---|
| 1 | SubAgent 内部工具调用 | 查几次、查什么;**含从记忆中主动发现异常模式并自行深挖** | ✅ V1 做 |
| 2 | 调和层回补 | 依据不足时是否退回补充查询 | ✅ V1 做 |
| 3 | 记录解析追问 | 输入模糊时是否追问、追问什么 | ✅ 已实现(2026-08-27)，见 D33，扩展覆盖 log_write + 四个 SubAgent 分支 |
| 4 | 未命中时外部检索 | 是否引入 web search | ⏳ 见 `PRD.md` §17.1 |
| 5 | 压缩重要性判断 | 固定阈值分层 vs 模型判断 | ⏳ 实现时定 |

**判据**(可复用):把链路画成流程图,**若每个箭头的走向在编码时都能确定,它就是 workflow**。

**关键区分:响应式 vs 主动式。** 用户问什么答什么是 workflow;系统从状态中察觉"连续三天同一主料"并自行判断是否值得提示,才是 agent 行为。第 1 项的价值主要在后者。

**理由**:

1. **可评估性优先于自主性。** 固定管线使每段可挂独立指标(M3/M4/M5/M13/M14),错误能定位到具体环节。自由规划的 agent 只能测最终输出,一旦出错无法归因
2. **可预测性对健康类场景更重要。** 用户每次得到的推理路径应当一致
3. **符合 Anthropic 的建议**:找到最简单可行的方案,只在确有必要时增加复杂度

**面试要点**:能说清"我评估后刻意把主链路保持为 workflow,并把 agent 行为收敛到五个位置",比声称"我做了 agent"强得多。**砍掉不必要的自主性是工程判断,不是能力不足。**

**同时修正 `PRD.md` §3 的论证结构**:原版三条论证中,前两条实际论证的是"需要 LLM 而非规则引擎",与"需要 agent 而非 workflow"是两个问题。已拆为 §3.1 / §3.2。

## D21 · 沙盒 / 代码执行:不做

**选择**:工具白名单维持"知识库检索、天气查询、记忆读写",不加 shell 或代码执行。
**放弃**:引入沙盒做数值分析。
**理由**:设想中需要计算的场景(如统计近期某主料出现次数)本质是 SQL 查询;引入代码执行会大幅扩大攻击面(OWASP LLM08 过度自主),而收益不明确。**大部分看起来需要计算的需求,其实是查询。**

## D22 · 领域能力是否 Skills 化

**选择**:把 D17 已经判定"做成工具/模板"而非 SubAgent 的能力(菜谱生成、购物清单),以及调和层的仲裁 rubric、核查 pass 的检查项清单,封装成独立的、可版本化的 Agent Skill 文件(每个 skill 一份说明 + 所需参考表),按路由结果或调用阶段按需加载进对应的那一次 LLM 调用,而不是常驻在中枢 system prompt 里。

**放弃**:
- 把这些能力的说明文字硬编码进中枢或对应 LLM 调用的 system prompt,长期常驻
- 做成第三个 SubAgent(已被 D17 排除)

**理由一 · 直接服务于 §12.3 的上下文预算。**
中枢 system prompt 预算只有 2.5k token,但菜谱/购物清单模板、调和层 rubric、核查 pass 的 7 条检查项(§10.1)如果都写死在对应 prompt 里,预算很快被常驻内容占满,而这些内容在大多数请求里根本用不上——只有路由结果命中"记录/菜谱"或触发调和/核查时才需要。Skills 的按需加载模型(只有被路由到的任务才把对应 SKILL 内容装进那一次调用)是这个预算约束的直接工程解法,不是为了用而用。

**理由二 · 与 D14/D15 的"独立可迭代"目标同源。**
调和层 rubric 和核查 pass 检查清单本来就要求"可独立迭代、不影响生成侧 prompt"(D15)。把它们做成有版本号的 skill 文件,天然获得这个属性,还顺带给了 `worknotes.md` 里一直空着的"prompt 迭代记录表"一个具体落点——每次改 skill 文件就是一行迭代记录。

**理由三 · 边界清晰,不越权。**
Skill 不获得独立上下文或独立 LLM 调用,只是被装进已有的某次调用(中枢自身、调和层调用、核查 pass 调用)的 prompt 里——这保持了 D14/D15"调和层与核查 pass 各自只有一次独立 LLM 调用"的性质不被破坏,区别于 SubAgent。

**判据(复用 D17 的候选评估表逻辑)**:候选能力若"说明性内容量大但只在特定路由分支需要"就适合做 Skill;若"每次推理都需要"就应该常驻;若"需要跨领域仲裁或独立评估"应该是 SubAgent(D1/D14)而不是 Skill。

**补充(2026-08-26,随 D25 一起补入)**:调和层 rubric 需要新增一条具体条款——用户明确表达的口味偏好与体质/目标建议的方向冲突时,默认给出"怎么吃更聪明"的调和建议而非单纯劝阻,除非命中过敏原/ED 硬性阻断规则。这条原则不是新的 Skill,是给已经决定要做的调和层 rubric 文件补的一条内容,详见 D25。

**补充(2026-08-26,增补两个新 Skill,并记录被否决的候选)**:重新用本条的判据("说明性内容量大但只在特定分支需要"→Skill;"每次推理都需要"→常驻;"需要跨领域仲裁或独立评估"→SubAgent)过一遍还没被考虑过的候选能力,结果是新增两个、否决五个。

**新增**:

| Skill 文件 | 内容 | 加载时机 | 为什么符合判据 |
|---|---|---|---|
| `backend/skills/ccmq_questionnaire.md` | CCMQ 简版问卷的题库(九类体质各自的条目)、追问话术、"不确定"选项的处理方式、D28 §11.3 的计分口径说明 | 首次使用引导对话流程走到问卷分支时(D28,ARCHITECTURE.md §11.2 步骤 3b) | 内容量大(九类体质的题目与计分口径)且只在引导流程这一条路径上用得到,不该常驻在中枢 2.5k 的 system prompt 预算里 |

- **节气/季节性调理细则**——这是事实性知识,已经在 `retrieve_tcm` 的知识库里,通过 RAG 检索获取,不是"指导模型怎么判断/怎么表达"的指令性内容,不符合 Skill 的定位(D22 判据本身就是拿"指令性内容 vs 事实性知识"做区分的,后者该扩充知识库而不是加 Skill)
- **候选评估分支的候选真实性预检查**——内容和 `verification_checklist.md` 里 D25 新增的候选评估专用规则高度重叠,单独拆一份文件的边际内容量不够,不满足"内容量大"这条判据
- **追问澄清策略(何时该反问用户而不是直接给答案)**——本身是有价值的能力,但目前六条分支(D12/D25)里没有一条对应"主动反问"这种分支外的行为,加这个 Skill 前需要先在路由层面决定要不要开一个新的交互模式,这是比"要不要做 Skill"更上层的产品决策,记入 `PRD.md` §17 开放问题,不在本条直接否决为"不做",而是标记为"顺序不对,不是现在做"

## D23 · RAG 全链路:格式转换 / 切块 / embedding / 存储

**选择**:

1. **格式转换**:不引入 markitdown 类"万物转 Markdown"统一转换器。结构化格式(JSON/JSONL/XML/MD)按原生结构解析,保留字段语义;PDF 按内容类型分流——表格密集的(`GB7718-2025.pdf`、`Daily Serving Sizes.pdf`)用 Docling,纯文字的继续用 pdfplumber。
2. **切块**:在 D3"结构优先切分"基础上加一层 token 感知二次切分——用目标 embedding 模型自己的 tokenizer(不是字符数,不是 jieba 分词数)给每个 chunk 计数,超阈值的按句子边界二次切,过小的与相邻块合并。
3. **Embedding**:双档策略,复用 D19 的模型分层思路——开发迭代期用 **BGE-M3**(开源、本地、免费、中文强);正式交付/跑分档用 **Voyage**(API,多语言表现扎实,成本低于 OpenAI/Gemini 同档)。
4. **存储**:**不引入独立图数据库**(Neo4j 等)。冲突规则、体质-食材等关系型知识用 Postgres 普通关系表 + 外键建模,多跳查询用 `WITH RECURSIVE`;向量检索维持 D4 的 pgvector 方案;三者(向量检索、关系型图结构、D18 的用户记忆)共用同一个 Postgres 实例。

**放弃**:
- 用 markitdown 统一转换所有格式(会把 JSON/XML 的可用结构拆掉再让模型自己猜回来)
- 固定字符数切块(D3 已经放弃过一次,这里是重申)
- 用 jieba 等分词器辅助 embedding 阶段的中文处理(现代 embedding 模型自带子词分词器,不需要)
- 引入 Neo4j 等独立图数据库做冲突关系推理

**理由**:详细的选项对比、评测数据来源、逐条推理见 `docs/RAG_PIPELINE_DESIGN.md`。这里摘要一条最容易被追问的:**为什么不上图数据库**——当前关系数据规模(40 条冲突规则、9 种体质、106 种食材)远没到图数据库性能优势体现的量级,且 D18 已经把用户记忆放进同一个 Postgres,继续用同一个实例(关系表建模图结构 + pgvector)比引入第二套数据库系统更符合 D4"单机部署简化交付"的既定精神。如果 V2 关系复杂度显著上升,再引入图数据库是加一层,不是推倒重来——节点/边的数据已经在关系表里,不需要重新建模。

**面试要点**:能说清"我评估过图数据库,但当前数据规模和查询模式不支撑引入第二套系统,用同一个 Postgres 的关系表 + 递归 CTE 就够了",比"我上了向量库+图数据库的混合检索架构"更诚实、更站得住——后者在只有几十条规则的项目里会被面试官一眼看穿是过度设计。

**实现进展(2026-08-26)**:
- pdfplumber 路径(Docling 不可用/不可信时的主路径)已实现并用真实 PDF 验证:`_merge_pdf_table_header()` 修了 `Daily Serving Sizes.pdf` 一个真实存在的表头跨行 bug(旧代码把表头第二行当数据行解析,产出过明显乱码的 chunk),细节见 `knowledge/_raw/README.md` §9。
- Docling 路径(`ingest_pdf_tables_docling()`)用户在自己有网络的机器上装好后实测跑通了,但**结果比 pdfplumber 启发式更差**:对 `Daily Serving Sizes.pdf` 这张 3 层合并表头的表,Docling 不报错但静默输出了错误结果(列名串味、跨列数值合并),而对同一 PDF 里表头只有一行的简单表(第3页)Docling 处理完全正确、和 pdfplumber 一致。说明问题不是"Docling 不可用",而是"复杂合并表头的表格结构识别在这个具体案例上不如手写启发式可靠,且是静默错误,不做人工核对会被当正常数据用进去"。据此把 D23 原文里"表格密集的用 Docling"这条**收窄**:`ingest.py` 里 `Daily Serving Sizes.pdf` 改回直接调 `ingest_pdf_tables()`(pdfplumber),不再自动优先 Docling;`ingest_pdf_tables_docling()`/`ingest_pdf_tables_auto()` 保留在代码里,留给结构简单的表或以后处理 `GB7718-2025.pdf` 时按需人工验证后使用,不再作为默认路径无条件信任。
- BGE-M3 → pgvector 的落地脚本(`db/embed_bge_m3.py`)已写完(`load`/`search` 两个子命令,UPSERT 幂等,写入前 L2 归一化),对应的 `knowledge_chunks` 表已建入 `db/schema.sql`。**尚未执行过**——本项目目前没有已部署的 Postgres 实例,且需要在有网络、装好 `FlagEmbedding`/`torch` 的机器上运行。

## D24 · "按食材查菜谱"走 RAG 还是 SQL

**背景**:2026-08-25 把 XiaChuFang Recipe Corpus(下厨房菜谱学术数据集,155 万条,详见 `knowledge/_raw/README.md`)的前 5000 条按 D23 的切块方式收进了 RAG 语料(一条菜谱 = 一个 chunk),目的是支撑"给定原材料,推荐搭配的菜谱"这个功能。

**选择**:

1. "按食材查菜谱"这个具体查询模式**不进 RAG 语义检索**,落一张 Postgres 关系表 `recipes`(`ingredients TEXT[]` + GIN 索引,见 `db/schema.sql`);D17 已经把菜谱定为"工具"而非 SubAgent,D24 进一步明确这个工具内部该查哪一层存储——结构化过滤查数据库,不是语义检索。
2. RAG 语料里的 5000 条 recipe chunk 保留,但职责收窄为"给定模糊/开放式意图(比如'剩菜能做什么,随便推荐一个清淡的')时的语义召回补充",不再承担"精确按食材匹配"这条主路径。
3. `recipes` 表继续放进 D4/D18 已经在用的同一个 Postgres 实例,不新增数据库组件。

**放弃**:
- 完全依赖 RAG 语义检索回答"含有 X、Y 食材的菜"这类查询——BM25/embedding 检索返回的是"语义最相似的 top-k",不保证"一定包含某个词",这是检索方式本身的局限,不是能靠调参数解决的
- 单独起一个 Elasticsearch 之类的全文检索引擎——GIN 索引 + 数组包含在这个数据规模(百万级)下已经够用,呼应 D23"不引入图数据库"的同一条精神:数据规模和查询模式不支撑,就不加新组件

**理由**:这不是纯理论推演,是有实测数据支撑的。把 5000 条 recipe chunk 加进语料后重新跑 BM25 eval(23 条查询,PRD §8.4 B0 baseline),recall@5 从 60.9%(14/23,5112 chunk)**掉到** 56.5%(13/23,10112 chunk)。具体案例:"微波炉加热会破坏营养吗"这条查询,本该召回 `evidence-notes.md` 里讲微波法营养保留率的证据段落,结果被三条菜名/做法里恰好出现"微波"字样的菜谱(比如"生酮免烤微波炉版重芝士蛋糕")挤出了前五名——因为关键词检索只统计字面词频,不理解"用微波炉做蛋糕"和"微波会不会破坏营养素"是两个完全不同的话题。这正是"精确过滤类查询不该走相似度检索"的一个具体反例,而不只是设计直觉。

**面试要点**:不是所有检索问题都该无脑上 RAG——"含有某食材"是精确/包含过滤,关系数据库的 GIN 索引比强行凑一个向量检索方案更简单、更快、更准;能用自己实测出来的 recall 下降数字(而不是纯理论)证明这个判断,是比"我们上了 RAG"更扎实的工程叙事。

## D25 · 路由分支从四条扩到六条,补"记录回顾"与"候选评估";用户画像新增口味/情境偏好字段

**背景**:2026-08-26,`docs/ARCHITECTURE.md` 写完后,按用户交互场景做了一轮走查——枚举一批贴近真实使用的问法,逐条对照 D12 现有的四条路由分支(记录/事实查询/单领域/完整推荐)看能不能装下。走查用的问法包括:

- "我昨天晚上吃了什么,我都忘了"
- "我过敏,建议不吃什么类型的食物?" / "今天晚上这些可以吃吗?"
- "我今天已经吃了某个大补的东西,还能吃什么、不能吃什么?"
- "加班到很晚了,晚饭吃点什么,吃多少比较好"
- "楼下有黄焖鸡、米线,我选哪一个吃"
- 不同人群的关注点差异:爱运动的 / 不爱运动的、办公室需要轻食的、"馋辣但还是希望尽量健康,有没有什么 tip"

逐条核对后,发现两类问法在现有四条分支里都找不到合适的位置,另有一类问法揭示了一条隐含但没写明的产品原则。

**选择**:

**1. 新增"记录回顾"分支。** "我昨天晚上吃了什么"这类问法,原本会落进 D12 的"事实查询"分支(该分支的示例是"红枣是什么性味"),但两者检索的目标完全不同:事实查询查的是 `knowledge_chunks`(静态知识库),这类问法查的是用户自己的 `diet_log`(个人历史记录),连底层工具都不是同一个(`retrieve_tcm`/`retrieve_nutrition` vs `query_diet_log`)。合并成一条分支,会让路由决策(M13)在"查知识库"和"查自己的数据"这两件本质不同的事之间失去可训练的边界。新分支直接调用 `query_diet_log`,不经过 SubAgent,是全链路里最轻的一条路径。

**2. 新增"候选评估"分支。** "这个我现在能不能吃""楼下黄焖鸡和米线我选哪个""已经吃了大补的东西,还能吃什么"这三类问法有一个共同结构:用户给定了具体候选(一个或多个已知选项),要求系统给出取舍判断,而不是从零生成一份新方案。这和"单领域"/"完整推荐"两条分支的产出物(生成一份新方案 + 菜谱 + 购物清单)在任务框架上不同,虽然管线高度复用(仍然要过双 SubAgent + 视候选数量决定是否调和 + 核查),但 prompt 里"生成"还是"评估给定候选"这个框架不同,若不区分,核查 pass"每条建议有 source_id"这条规则在两种输出形态下会失去统一含义(候选评估的输出是"结论 + 理由",结论本身不是一条可挂 `source_id` 的独立建议条目)。核查 pass 因此需要为候选评估分支单独加一条规则:结论必须能拆解出至少一条带 `source_id` 的支持理由,而非要求结论字符串本身携带 `source_id`。

**3. 用户画像新增 `preferences` 字段,与目标标签(`goal_tags`)明确区分。** "办公室没法热饭""不吃香菜""能吃辣"这类问法暴露了一类现有字段装不下的信息:目标标签(`weight_management` 等)回答的是"身体希望往哪个方向调理",这类偏好回答的是"在满足调理方向的前提下,方案要符合哪些约束"——不是同一件事,不该合并进同一套字段。持久性的口味/情境偏好进 `user_profile.preferences`,由用户主动填写/确认后写入,遵循与过敏原字段相同的人在环原则(不从对话隐式推断)。一次性的情境信息(某一次"今晚加班到很晚")不建字段,随对话原文进入 SubAgent 任务上下文,靠模型的语言理解直接吸收——为每一种可能出现的场景都建一个结构化字段是过度设计。

**4. 调和层 rubric 补充一条 harm-reduction 语气原则。** "馋辣但还是希望尽量健康,有没有什么 tip"这类问法揭示的不是分支缺口,而是调和层目前没有显式写明的一条姿态:用户明确表达"想吃不那么健康的东西"时,系统默认应该给出"怎么吃更聪明"的调和建议(比如"想吃辣可以,搭配一些清热的配菜、少放油"),而不是"不建议吃"——除非命中过敏原/ED 这类硬性阻断规则。这条原则补进 D22 已经决定要做的调和层 rubric Skill 文件里,不是新增决策,是给已有决策补内容。

**放弃**:
- 把"记录回顾"并进"事实查询"——检索目标不同,合并会让路由判据变得模糊
- 把"候选评估"并进"完整推荐"不做区分——核查 pass 的判定标准和输出格式不一样,合并会让 M14 的评估口径混乱
- 单独为"候选评估"新增专门工具——评估候选和生成推荐复用的是同一套检索/记忆/规则表工具,区别只在 SubAgent 收到的任务描述(prompt 层面),不需要新工具
- 为"运动习惯""加班到很晚"这类一次性情境信息单独建结构化字段——这类信息随对话原文直接进入 SubAgent 上下文即可,建字段是过度设计(与 D17 排除运动/生活方式 SubAgent 的判断精神一致)

**"楼下黄焖鸡和米线选哪个"确认了一条 Non-Goal 边界**:系统不接入地图/餐馆点评类外部数据,不知道用户楼下实际有哪些餐馆、这些餐馆的实际配方。候选评估分支处理的是"用户报出的候选名称",按该类菜式的一般营养/食性属性组成判断,不验证候选是否真实存在、不做具体商户推荐。这条边界原来隐含在 PRD §6.2"不做采购下单集成"里,但没有显式覆盖"评估用户报出的现成选项"这个场景,借这次走查显式写进 PRD §6.2。

**理由(这条决策本身的方法论价值)**:产出方式不是先验地设计路由分支,而是先枚举一批贴近真实使用的问法,逐条核对能不能装进现有分支,装不进去的地方才是真正的缺口。这和 D9"eval ground truth 独立于实现"、D23"用真实 recall 数字而非理论推演做决策"是同一种工作方式的延续——用具体场景/数据倒逼设计,而不是反过来用设计去凑场景。

**面试要点**:能具体说出"我新增的每一条路由分支,背后都对应一个装不进现有分支的真实问法"，比"我设计了六条路由分支"更有说服力——前者证明扩展是被真实使用场景倒逼出来的,不是拍脑袋加的复杂度。

## D26 · 后端 Web 框架:FastAPI

**背景**:`ARCHITECTURE.md` §8 的目录结构里一直写着"`api/main.py` FastAPI",但这只是随手写的文件树注释,从未作为正式决策存在过——没有对比过备选方案,也没有把它和已有决策(D1 SubAgent 并发调度、D7 MCP server、M10 首字节延迟指标)显式连起来。这条决策把这个隐含假设显式化。

**选择**:FastAPI 作为唯一的后端 Web 框架,承载 REST + SSE 流式接口。

**放弃**:
- Flask(+ 手动接 Gunicorn/gevent 做异步):同步优先的设计和 D1 的 `asyncio.gather` 并行派发、SubAgent 独立超时控制天然不匹配,要拿到等价的并发能力需要额外中间件拼凑
- Django(+ DRF):自带 ORM/Admin/模板引擎等一整套本项目不需要的功能,单一后端服务不需要这些,徒增学习和维护成本,和 D21"不引入不必要组件"的一贯立场冲突
- Node.js/Express 另起一个网关层,Python 侧只做纯 agent 逻辑:引入跨语言边界,MCP server(D7)、LLM adapter(D19)、SubAgent 全部是 Python,新增一层语言边界只为了网关这一件事,收益不成立

**理由**:

**理由一 · 原生异步,和 D1 的并发模型是同一套编程模型。** D1 的双 SubAgent 派发用 `asyncio.gather(..., return_exceptions=True)`;FastAPI 的路由处理函数原生支持 `async def`,请求处理本身、SubAgent 派发、LLM adapter 调用(D19)可以是同一条 `await` 链,不需要在"同步 Web 框架"和"异步业务逻辑"之间加一层线程池桥接。

**理由二 · SSE 流式输出是一等公民,直接服务 M10。** PRD 把延迟拆成首字节和端到端两项(D11),`完整推荐`分支的核查 pass 通过后需要流式吐出结果(§5.2 步骤 8)。FastAPI 的 `StreamingResponse` 配合一个异步生成器就能实现 SSE,不需要额外的 WebSocket 握手开销,前端(Next.js)用标准 `EventSource`/`fetch` 流式读取即可对接。

**理由三 · Pydantic 模型是请求/响应 schema 与内部数据结构的同一套定义。** `dish_ingredient_map` 拆解结果、核查 pass 的判定结构、`conflict_rules` 命中结果——这些结构已经在 §4/§5 里以隐含 schema 的形式存在。FastAPI 强制用 Pydantic 模型声明请求体和响应体,这些模型可以和 MCP server(D7)工具的输入/输出 schema 复用同一套定义,避免"API 层一套 dataclass、MCP 工具层另一套 dataclass"的重复维护。

**理由四 · 自动生成的 OpenAPI 文档是加分项,但不是选择的主因。** `/docs` 自动可用,面试时可以直接打开演示接口契约,但这只是锦上添花——决定性的是理由一到三。

**未决细节(留给实现时)**:认证/会话机制(V1 单用户,§1.2 已注明"单用户可以只有一行"——是否需要一个最简单的 session cookie 还是完全跳过认证,留到接前端时定,不影响本决策)。

**面试要点**:框架选择本身不是难点,难点是"为什么不是随手选一个能跑的框架就行"——FastAPI 被选中是因为它的异步模型、流式响应、schema 校验三个特性分别直接服务于 D1(并发派发)、D11/M10(流式首字节延迟)、D7(schema 复用),不是因为"流行"或"简历好看"。

## D27 · 记忆架构升级:压缩优先级、结构化归档摘要、SubAgent 循环状态提示、认知类型反向验证(修订 D8)

**背景**:2026-08-26,对照《AI Agents in Depth》(Bojie Li 著)第 2、3 章及公开的 Mem0/Memobase 案例研究,重新审视 D8 的分层压缩设计与 §4 的三层记忆设计。原设计(D8/§4.1)已经把记忆分成"常驻上下文/数据库查询/会话历史"三层,方向是对的,但存在三处可以做得更扎实的地方:(1)压缩时"要不要先删工具调用产生的原始内容"没有显式回答;(2)`user_profile`/`diet_log` 这类字段的存储格式选择(为什么是结构化字段而不是自然语言笔记)没有被论证,只是隐含这样做了;(3)SubAgent 唯一的自主循环(D20 行为点 #1)缺少一个轻量的、code 维护的状态提示,模型完全靠自己数"我已经调用几次工具了"。

**关于调研范围的说明**:该书没有单独章节比较"Pine agent"或"DeepSeek harness"的记忆架构——Pine AI 是作者本人任职的公司(书中多处案例来自 Pine 的真实生产实践),但书中出现 Pine 的地方集中在第 9 章语音交互的"快慢思考解耦"案例,不是记忆设计专节;"DeepSeek"仅在第 2 章思考题里以"R1 与 V4 对历史 `reasoning_content` 去留策略相反"这一个具体例子出现,同样不是记忆架构专节。以下结论主要来自书中第 2 章(状态栏、压缩策略)、第 3 章(用户记忆系统、Mem0/Memobase 案例研究)、"Learn Claude Code" 资料展示的 GSSC pipeline / 四类记忆架构图,以及用户既有认知(working/episodic/semantic 三分法)。引用时如实标注来源,不夸大某个具体来源的针对性。

**选择**:

**1. 压缩优先级表:明确工具调用/检索原始内容是最先丢弃的一层,不与会话原文同等对待。**

现有 D8 的 Tier 0-3 已经把"会话历史"分了层,但"检索结果"(D18 之后压缩对象收窄为"会话历史 + 检索结果")一直被笼统地和会话历史用同一套 Tier 处理。参考书中反复强调的压缩优先级(架构决策/关键约束 > 修改记录/结论 > 校验通过/不通过状态 > 未解决事项 > 原始工具输出——最后一类是唯一"允许直接删除、不需要先摘要"的一类),给 §4.4 的分层压缩补一条显式规则:

| 内容类型 | 处理方式 | 理由 |
|---|---|---|
| 检索到但最终未被结论引用的 chunk | 压缩触发时直接删除,不摘要 | 摘要噪声本身就是浪费——一条检索结果如果最终没进最后的结论,说明它对当前判断没有价值,没必要先花一次 LLM 调用去总结它 |
| 检索到且被结论引用的 chunk | 只保留 `source_id` + 一句话结论,原文可丢弃 | 溯源展开(§5.2 步骤 8)靠 `source_id` 回查数据库,不需要在会话历史里留一份检索原文的副本——这是重复存储 |
| 调和层/核查 pass 的结论与理由 | 保留结构化摘要(见第 2 点) | 对应书中"架构决策/关键约束"优先级最高的一类——这是本次交互真正有价值的产出 |
| 未通过核查、被移除的建议条目 | 保留"被拒绝 + 拒绝理由"这一行,不保留完整原文 | 对应"未解决事项/校验状态"这一类——下次遇到类似输入时,这条记录本身就是一条有用的负样本,但不需要携带它当时的完整生成内容 |

**这条规则回答了最初的问题("工具调用的记忆是不是可以先删掉")——答案是肯定的,且是本书态度最明确的一条压缩原则,不是本项目自己拍脑袋得出的。**

**2. 结构化归档摘要,替代自由文本摘要。** §4.4 的 Tier 2("摘要成结论句")原来没有规定摘要的具体形式,改为固定模板而非自由文本 LLM 摘要:

```
{turn_id} | {branch}(六条分支之一) | 结论:{一句话} | 引用:{source_id 列表} | 被拒建议:{若有} | 触发的 guardrail:{若有}
```

类比书中"归档摘要像 `git log` 不是 `git squash`"的说法:每条摘要是一行独立的、结构化的记录,而不是把多轮对话揉成一段无法拆解的自由文本。直接好处是 Tier 3(跨会话摘要)可以被结构化查询(比如"上次因为过敏原被拒绝的建议是什么"),自由文本摘要做不到这一点。

**3. 用"认知类型"这把尺子回头检查 §4.1 的三层设计,发现它已经覆盖了主要类型,程序性记忆是有意排除的非目标。**

| 认知类型(书 §3.1.5) | diet_expert 对应内容 | 现有位置 |
|---|---|---|
| 语义记忆(稳定的一般性知识) | `user_profile` 里的体质/过敏原/`preferences`/`goal_tags`/`trend_tags` | §4.1 常驻上下文 |
| 情景记忆(具体事件) | `diet_log` 明细、`conversation_sessions` 的单轮记录 | §4.1 数据库查询 + 会话历史 |
| 程序性记忆(行为模式) | **V1 明确不做**——推荐流程本身是固定的 D20 workflow,不是"系统从用户历史交互里学出来的做事方式";没有真实场景需要"系统记住自己上次是怎么处理某类请求的"这类元层面的行为模式 | 非目标,显式记录避免以后被误当成遗漏项补上 |

结论:现有三层设计已经对应了语义/情景两类记忆,程序性记忆是有意排除的非目标,不是遗漏——这次调研的价值是把这个隐含判断显式化、可回查,而不是推翻重来。

**4. 用"存储格式四分法"(Simple Notes → Enhanced Notes → JSON Cards → Advanced JSON Cards)反向验证 D25 的字段设计,并发现一处需要补强的地方。**

书中的选择标准是:关键、低容量 → Advanced JSON Cards(需要可追溯、可消歧);大容量、非关键 → Simple Notes(压低成本)。对照:

- `user_profile` 的 `allergens`/`preferences`/`constitution` 完全符合"关键、低容量"——这验证了 D25 把它们做成结构化字段(而不是一段自由文本"用户备注")是对的方向,但**目前的字段设计还不是完整的 Advanced JSON Cards**:Advanced JSON Cards 的核心是每条记忆带 `backstory`(为什么记下这条)和来源/时间戳,而现有 `allergens TEXT[]` 这类简单数组只有值,没有"这条信息是什么时候、以什么方式确认的"。**这一点在体质字段上最关键**,直接导出 D28 的 `constitution_source`/`constitution_confirmed_at` 设计,不是空谈。
- `trend_tags`(从 `diet_log` 周期性聚合出的"最近偏肥甘厚味"这类判断)符合 Simple Notes 的定位——一句话结论,访问频繁但容错率高,不需要 Advanced JSON Cards 的开销,现有设计已经是对的,不改。
- `diet_log` 本身不套用这四分法——它是结构化的事务性日志(有 schema、走 SQL 聚合查询),不是"记忆系统"意义上的叙事性笔记,四分法讨论的是"记忆条目怎么表示",不适用于本来就该建表的结构化业务数据,§1.2 的做法已经是对的,借这次调研明确边界,避免以后有人想"用 Advanced JSON Cards 格式重做 diet_log"这种不必要的返工。

**5. SubAgent 循环新增一个 code 维护的状态提示(不是完整的"状态栏"系统)。**

D20 把"agent 行为"限定在五处,其中行为点 #1 是"TCM/Nutrition SubAgent 可多次检索、可自行判断是否继续"——这是全链路里**唯一**一处模型自主决定"要不要再调用一次工具"的地方(路由、调和、核查都是固定 workflow 步骤,不是开放式循环)。书中状态栏的核心价值场景正是"开放式多步循环里,模型需要知道自己走到哪一步、预算还剩多少",这个价值只在这一处适用,不需要给整条六分支 workflow 都装状态栏。

**具体设计**:在 SubAgent 每一轮决定"是否再调用工具"之前,由代码(不经过任何 LLM 调用)拼接一条状态消息,追加到该 SubAgent 上下文的末尾(书中强调:必须在最新位置,且必须是代码计算而非模型自己总结——模型自己总结的状态栏在实验里表现更差):

```
[状态] 已用工具调用:{n}/15(资源限额,§5.4)· 已检索到的候选信息要点:{code 生成的短列表,不是全文摘要}
```

"已检索到的候选信息要点"不是自由文本摘要,是从已发生的 `tool_use`/`tool_result` 事件里用确定性规则抽取的短列表(比如已查过哪些食材、已查过哪几天的天气)——这仍然遵守本条第 1 点"工具调用原始内容优先丢弃"的原则,状态提示本身不携带任何原始检索文本,只携带"发生过什么"这一层元信息。

**明确的风险提示(书中称为"状态栏投毒")**:如果这条状态消息本身算错了(比如次数统计有 bug),模型会无条件信任它,错误会直接传导成错误决策。因此这段代码本身需要被单测覆盖(呼应 ENGINEERING §7.3"确定性优先"——这是少数几处"越确定性、越该测"的代码路径之一),不能等到集成测试才发现计数错了。

**放弃**:
- 给中枢 agent 的六条分支路由或调和层/核查 pass 也加状态栏——这几处都是固定 workflow 步骤(D20),不存在"模型自主决定要不要继续"的问题,状态栏在这里没有对应的决策场景,加了只会占用宝贵的 prompt 预算(§12.3)
- 照搬"Learn Claude Code"的 `user`/`feedback`/`project`/`reference` 四类记忆分类作为 diet_expert 的记忆 schema——这四类是为**长时程自主维护同一个代码库**的 coding agent 设计的(`user` = 编码风格偏好,`feedback` = 测试规范这类"怎么做事"的经验,`project` = 为什么在做这次重构,`reference` = 去哪查线索),对应的是"一个 agent 跨很多次会话持续维护同一个复杂制品"这个场景。diet_expert 是"单一 session 内给出一次性推荐"的对话式产品,没有 `feedback`(系统怎么做事的经验)和 `reference`(排查线索去哪找)这两类的真实使用场景——`reference` 比较接近的对应物是 RAG 检索本身自带的 `source_id` 溯源机制(§5.2 步骤 8),已经存在,不需要单独做成一类持久记忆。生搬四类分类会制造出两个用不上的空字段,这条反而印证了 D17/D20 一贯的"不为了模仿知名架构而制造不需要的组件"的立场
- 采用 GSSC(Gather-Select-Structure-Compress)命名重写现有 pipeline——走查后发现 §4.3(关键事实扫描)+ §5.1(路由)+ §5.2 步骤 2-3(任务上下文组装)+ §4.4(分层压缩)已经**收敛到和 GSSC 相同的四段结构**,只是命名不同。这是趋同验证,不是需要引入的新组件,不改代码,只在本决策里记一笔
- 引入 Mem0/Memobase 作为依赖——这两个是通用记忆中间件,本项目的记忆结构(体质/过敏原/口味的强类型字段 + 关系型 `diet_log`)比它们面向的"任意对话记忆"场景更窄、更结构化,直接用 Postgres 关系表 + JSONB 字段(已有 D4/D18/D23/D24 的既定方向)比接一个通用记忆框架更贴合;读它们的架构只是为了借鉴设计思路(比如 Mem0 v3"写入只 ADD、冲突留到检索时解决"这个思路,给本条压缩设计一点启发:`trend_tags` 的周期性重算本身就是"检索时/聚合时消解冲突",不需要额外改动)

**理由**:见"选择"每一小节内的分述,总体方法论与 D9/D23/D25 一致——用外部真实案例的具体机制反过来检验已有设计哪里经得住推敲、哪里是想当然,而不是照搬外部命名体系。

**面试要点**:这条决策最有叙事价值的部分不是"我们也用了状态栏"或"我们也做了分层压缩"——这两个词现在很容易说出口。有说服力的是能具体讲清楚**为什么状态栏只加在 SubAgent 循环这一处、不是所有地方**(因为只有这一处是开放式自主循环,其余都是 D20 定义的固定 workflow),以及**为什么放弃了四类记忆分类而不是照搬**(场景不匹配,生搬会制造空字段)——这两点合起来证明的是"读过参考架构、理解它解决的具体问题、再判断本项目是否有同一个问题",而不是"抄了一个听起来很专业的设计"。

**修订(2026-08-26,两处)**:

**修订一 · 程序性记忆重新纳入范围,不再是非目标。** 原决策第 3 点把程序性记忆判成"V1 明确不做",理由是"推荐流程是固定 workflow,没有系统需要记住自己怎么做事的场景"——这个理由对"系统层面的行为模式"成立,但漏看了一个更小、更具体、真实存在的场景:**用户自己反复使用的菜品说法**。§4.2 的菜品拆解已经承认 `dish_ingredient_map` 覆盖率不足时要靠 LLM 兜底,但没有设计"这个用户反复这样说,系统该不该记住"这条学习回路——这恰好是"从重复行为里学出一条可复用的做事方式"的教科书场景,程序性记忆这把尺子原本就是用来接住它的。

**具体设计——个人菜品简称表(`user_dish_aliases`)**:

| 字段 | 说明 |
|---|---|
| `user_id` · `normalized_phrase` | 归一化后的原始说法(去空白/标点),作为查找键 |
| `dishes JSONB` · `ingredients TEXT[]` | 上次 LLM 兜底给出、且被人在环确认未修改的结构化结果 |
| `hit_count` | 同一归一化说法被相同结构确认的次数 |
| `promoted_at` | 达到晋升阈值(建议 3 次)、正式生效可直接命中的时间;为空表示还在候选期,仍需过 LLM 兜底 |

**晋升规则是确定性代码,不是模型判断**:§4.2 步骤 1 的查表顺序从"`dish_ingredient_map` → LLM 兜底"两级,扩为"`dish_ingredient_map` → `user_dish_aliases`(仅命中已晋升的行)→ LLM 兜底"三级;每次 LLM 兜底路径的结果经人在环确认且未被修改,就把这条 `(user_id, normalized_phrase, 结构化结果)` 写入候选表并计数,计数达标才晋升——晋升前后都不需要模型参与判断"这条该不该记住",完全是计数阈值触发,这一点保持了 D27 原有对"确定性优先"的坚持,没有因为纳入程序性记忆就引入模糊的"模型自己觉得该记住"逻辑。

**为什么只做这一个场景,不做"交互风格偏好""拒绝模式学习"这类更泛的程序性记忆**:后两者的"该学什么、学到什么程度算对"本身定义不清(比如"用户上次拒绝了一条辣味建议"到底该被泛化成"这个用户不爱吃辣"——那已经是 `preferences` 该管的语义记忆——还是"这个用户在深夜问答时更容易拒绝辣味建议"这种更细粒度、更难验证的行为模式),贸然做等于在没有 eval 手段的情况下往系统里加一个不可验证的自适应黑盒,与 D9"eval ground truth 独立于实现"的精神冲突。菜品简称场景之所以安全,是因为它的"对不对"有一个客观标准——人在环确认过的结构化结果就是 ground truth,不存在"学错了"的模糊地带。

**放弃(修订后的补充)**:
- 把菜品简称个性化做成"语义记忆"塞进 `preferences` 或另一个 `user_profile` JSONB 字段——`preferences` 的语义是"口味/情境约束"(D25),菜品简称是"这个人这样说话时具体指什么",是完全不同维度的信息,混进同一个字段会让 `preferences` 的取值失去一致的语义
- 让模型判断"这条说法该不该晋升为个人简称"——见上,晋升必须是计数阈值,不是模型自由裁量

**修订二 · 压缩触发时机从"待定"改为具体设计。** 原 §4.4 只说"V1 先用固定阈值",没给出阈值和触发点本身。结合 PRD §12.3 的实际预算数字(中枢会话历史 ≤10k;SubAgent 检索结果 ≤12k、内部推理累积 ≤6k),补齐两级触发机制:

**SubAgent 内(单次请求生命周期内,同步,不需要 LLM 调用)**:每次 `tool_result` 追加后,与 §4.5 状态提示同一处代码顺带检查"检索结果"子分区的估算 token 数;超过其 12k 预算的约 80%(≈9.6k)时,按 §4.4 的压缩优先级表就地丢弃未被引用的 chunk,直到回落到阈值以下,再继续下一轮工具调用。这是纯内存操作,不落库、不异步,因为 SubAgent 的生命周期本来就只有一次请求那么长。

**中枢会话历史(跨轮次/跨会话,persistent 到 `conversation_sessions`)**:检查点在 §5.2 步骤 2(准备派发上下文,读会话历史)和步骤 9(会话落库)各有一次,职责不同:
- 步骤 9(响应已发出之后,异步):若当前会话的 Tier 1(原文轮次)累计估算 token 超过约 6k(会话历史 10k 预算的 60%,给 Tier 2/Tier 3 留出空间),对最旧的若干轮触发一次结构化归档摘要(§4.4 模板,需要一次低成本 LLM 调用),写入 Tier 2,原文本身可从 Tier 1 移除。会话被判定结束(空闲超过约 30 分钟无新消息,阈值待实测调整)时,把该会话全部 Tier 2 摘要进一步折叠进 Tier 3。这条链路和 `trend_tags` 的异步重算是同一个模式(§4.1),不占用当前请求的响应时间。
- 步骤 2(下一次请求组装上下文时,同步,只做兜底检查,不做真正的压缩工作):正常情况下步骤 9 的异步任务应该已经让 Tier 1 回落到阈值以下;万一没有(异步任务积压、失败,或短时间内连续多轮消息来不及处理),这里不等待、不同步调用 LLM 摘要(会话历史的摘要生成允许有延迟,但正在被回答的这一轮不能被压缩逻辑拖慢),而是直接应用 PRD §11 fallback 表已有的"丢弃最旧的低价值记录"——从 Tier 3 最旧的一条开始丢,而不是从还没来得及摘要的 Tier 1 丢(丢 Tier 1 原文等于丢了本该异步生成、还没来得及生成的摘要,信息损失更大)。

这套"正常路径异步、紧急路径同步硬兜底"的两层设计,直接对应书里"分层压缩既要控成本又不能拖慢关键路径"的立场,也和 D26(FastAPI,SSE 优先保证首字节延迟)的取向一致——压缩本身不应该出现在任何一次请求的关键路径耗时里。

**补充(2026-08-28,实现分层压缩算法时的两处具体设计,细化 D13/D27,不推翻原结论)**：

1. **压缩触发阈值按实际模型的上下文窗口缩放,不是照抄 PRD §12.3 的固定数字**。原 D27 修订二给出的"12k/9.6k"、"10k/6k"这些数字是按"中枢 agent 窗口足够大(≥32k)"这个假设设计的——如果实际配置的模型窗口比这个假设小(常见于本地小模型,比如某些量化过的 Ollama 模型只有 4k-8k 上下文),沿用没有缩放过的固定阈值会让"压缩逻辑觉得还没到该触发的时候"和"这次请求其实已经超出模型物理上限"这两件事脱节。新增 `backend/llm/model_capabilities.py`(和 `backend/observability/cost.py` 的 `_PRICE_PER_MILLION` 同一种前缀匹配表模式)登记已知模型的真实上下文窗口,`LLM_CONTEXT_WINDOW_OVERRIDE` 环境变量提供不用改代码就能生效的覆盖入口(本地模型/新模型都适用)；`backend/memory/compression.py` 的 `_effective_budget()` 用这个值缩放 PRD 假设的预算,**只收紧、不放大**——模型窗口比 32k 假设更大是常态,但预算数字本身是主动的成本/延迟决策,不是"模型能装多少就该塞多少",窗口更大不代表应该多用。这条设计直接落实 D13"PRD 定义能力档案(上下文长度…),具体模型作为可替换的实现注记"的原则——上下文长度就是这里说的能力档案字段,压缩阈值消费它,而不是把某个具体模型的窗口大小写死进压缩逻辑本身。

2. **压缩逻辑操作的 chunk 类型和检索结果的 `RetrievedChunk` 类型故意解耦**。`backend/memory/compression.py` 定义自己的 `CompressibleChunk`(只有 `source_id`/`text` 两个字段),不复用 `backend/mcp_server/tools/_retrieval_common.py` 的 `RetrievedChunk`——一是包依赖方向已有既定约束(`backend/agents/`/`backend/mcp_server/` 依赖 `backend/memory/`，反过来会成环，`dish_decomposition.py` 导入 `backend/llm/adapter.py` 的 `CompleteFn` 是这个方向的既有先例)；二是 `_retrieval_common.py` 文件名前缀下划线本身就表明"仅供 mcp_server 包内部使用"，跨包导入一个私有模块违反它自己的命名意图。调用方(以后接线中枢编排层时)把 `RetrievedChunk` 转成 `CompressibleChunk` 是一行代码，不值得为了省这一行牺牲包边界的清晰度。同理，压缩函数的 `cited_source_ids` 参数要求调用方直接传 `list[str]`，不在 `compression.py` 内部调用 `backend.agents.citation.extract_cited_ids()` 解析原文——那个函数在 `backend/agents/`，同一条依赖方向约束。

**补充二(2026-08-28，接进真实 `/api/chat` 请求生命周期，细化 D27 修订二)**：上面记录的"这次没做的部分"里，中枢会话历史两级触发(§4.4.1 步骤2/9)这一半已经补上——`backend/memory/session_store.py`(新文件)是 `compression.py` 和真实 Postgres 之间唯一的桥梁：`record_turn()` 写入这一轮原文并顺带检查 Tier1→Tier2 归档，`maybe_fold_idle_session()` 在新消息到达这个天然时机检查会话是否空闲、空闲则把 Tier2 折叠成 Tier3，`load_session_history()` 给下一轮组装上下文用。`db/schema.sql` 的 `messages` 表补了五列(`branch`/`conclusion`/`cited_source_ids`/`rejected_suggestions`/`triggered_guardrails`)——raw(tier0)行写入时就填好，归档时不用重新解析 `content` 才能拿到这些字段。

三处值得记录的具体设计判断：

1. **不改 `backend/agents/dispatch.py` 任何函数签名去传递"这一轮发生了什么"**。`dispatch_branch()`/`stream_multi_task()` 已经把这些信息完整编码进标准化的 SSE 事件协议里(`token`=结论文本、`source`=引用、`guardrail`=触发的guardrail/被拒建议)——`api/main.py` 新增 `_TurnAccumulator`/`_parse_sse_chunk`，直接观察已经产出的事件流重建 `TurnRecord`，比在 `dispatch.py` 内部一路往下传一个"累加器"对象更不侵入，也更符合那个模块"只管产出 SSE 事件，不管这些事件之后怎么被消费"的既有职责边界。

2. **写入用 `asyncio.create_task(asyncio.to_thread(...))`，不 `await`**——这个项目没有 Celery 这类真正的后台任务队列，`create_task`+`to_thread`(避免同步 psycopg2 调用阻塞事件循环)是"不占用当前请求响应时间"在 FastAPI 原生语境下的直接等价物。代价：这是一次性、不追踪结果的后台任务，进程在任务跑完前退出会丢这一次归档(不是丢用户已经拿到的响应，只是压缩/归档这个锦上添花的动作)，可接受。

3. **会话历史只接给会派发 SubAgent 的四个分支(`fact_query`/`single_domain`/`candidate_eval`/`full_recommend`)，不接给 `log_write`/`log_review`/`other`**——后三者本来就不需要跨轮次上下文也能正确处理这一轮(写日记不需要看历史对话、查记录直接查数据库、闲聊快速通道本来就是无状态的)，`dispatch.py` 新增的 `_compose_task_input()` 只在这四条路径上被调用，历史文本作为"供参考背景"的独立小节拼在用户消息前面，不直接拼接——避免 SubAgent 把历史里的旧结论误当成这次问题本身的一部分去回答。

**Level 1 已按 FIFO 接线(2026-08-29)**：`run_agent_loop` 在每次 retrieve_* `tool_result` 后调用 `fifo_drop_oldest_chunks`。循环中途不能按「未引用」丢弃（`final_text` 尚不存在）。`compress_retrieved_chunks`（引用感知）仍留给循环结束后的归档路径。

**真实验证(2026-08-28，本地真实 Postgres + 本地真实 uvicorn)**：`fact_query`/`other`/`single_domain` 三种分支各发一条真实 `/api/chat` 请求，直接查 `messages` 表确认每条都出现了带正确 `branch`/`conclusion`/`triggered_guardrails` 字段的行(其中一条因为默认种子画像的过敏原命中被核查拦截，`conclusion` 为空但 `triggered_guardrails`/`rejected_suggestions` 正确记录了拦截原因——证明失败路径也被如实记录，不是只有"成功"路径能生成一条 turn)；`tests/integration/test_session_store.py`(12条)对真实 Postgres 验证了写入/归档/折叠/读取四个函数；`test_api_chat_sse.py::test_session_history_is_forwarded_into_subagent_task_input` 用注入的假历史文本验证读侧确实传到了 SubAgent 收到的 `complete()` 调用里。

## D28 · 首次使用引导流程与体质获取对话化(细化 D5,新增 `constitution_source`/`constitution_secondary` 字段)

**背景**:D5 定案"体质获取用 CCMQ 简版问卷自评",但没有回答三个具体问题:(1)问卷什么时候触发,是不是必须作为注册时的强制前置步骤;(2)用户如果已经知道自己的体质(比如去中医院测过),要不要还是走一遍问卷;(3)CCMQ 计分本身经常出现"多个体质同时达标"(中医"体质夹杂"是常见结果,不是异常情况),现有 `user_profile.constitution TEXT`(单值字段,§1.2)装不下这种情况——这一点在"待决问题"表里已经以"体质字段是否随记录漂移"的形式被隐约提到,但没有被认真处理过。

**选择**:

**1. 不做强制前置问卷,做"渐进式引导"。** 首次会话(判定条件:`user_profile` 不存在,或存在但核心字段——过敏原/体质均为空)第一轮由系统主动说明:会先了解一些基本情况(过敏原、体质、口味),每次几个问题,随时可以跳过,跳过不影响使用基础功能(事实查询、记录分支不依赖体质字段)。不做成一次性表单,理由和产品定位一致(PRD 定位是对话式 agent,不是注册表单),也避免用户在第一次接触产品时就被十几个问题劝退。

**2. 体质获取先反问"是否已知",分两条路径。**

```
系统:"你知道自己的中医体质类型吗?(比如气虚质、阳虚质这些)"
   │
   ├─ 已知 → 直接询问是哪一类(九分类之一) → 写入 constitution
   │         + constitution_source = "self_reported"
   │         + 人在环确认(PRD §10.2,即便是用户自述,也过一遍确认展示,而非直接采信——
   │           自述可能记错、可能是几年前测的、术语可能用错)
   │
   └─ 不知道/不确定 → 对话式 CCMQ 简版问卷(非一次性表单):
             每轮抛 2-3 题,允许"不确定"选项,收集完整轮次后计分
             │
             计分:CCMQ 简版每题 5 级量表,按九类体质分别算转化分(0-100)
             判定:转化分 ≥ 40 记为"是",30-40 记为"倾向是"——**可能同时命中多个体质**
             (中医里"体质夹杂"是常见结果,不是异常)
             │
             呈现:"根据你的回答,你的主要体质倾向是 X;同时有一定 Y 质的特征"(若有次要体质)
             │
             人在环确认:确认 / 修改 / "不太准,先跳过"
             │
             写入:constitution(主)+ constitution_secondary(次,可空,数组)
                  + constitution_source = "ccmq_computed" + constitution_confirmed_at
```

**3. `user_profile.constitution` 从单值 `TEXT` 改为"主 + 次"结构,并新增来源与确认时间字段。** 这是对 §1.2 现有 schema 设计的一处修订:

| 字段 | 类型 | 说明 |
|---|---|---|
| `constitution` | `TEXT` | 主体质(九分类之一),CCMQ 计分下最高转化分对应的类型,或用户自述 |
| `constitution_secondary` | `TEXT[]` | 次要体质(可空),CCMQ 计分下达到"倾向是"阈值但非最高分的类型;用户自述路径下通常为空 |
| `constitution_source` | `TEXT` | `self_reported` \| `ccmq_computed` \| `unconfirmed` | 来源直接影响 TCM SubAgent 给建议时的置信度语气——呼应"存储格式四分法"里 Advanced JSON Cards 的 `backstory` 概念(D27):不只存值,还存"这个值是怎么来的" |
| `constitution_confirmed_at` | `TIMESTAMP` | 人在环确认发生的时间;为空表示还没走过确认流程 |

**这条修订同时回应了"待决问题"表里"体质字段是否随记录漂移"这一项**:字段本身不随每次饮食记录自动漂移(那样会破坏"体质是相对稳定的个人属性"这一医学前提),但 `constitution_confirmed_at` 让"多久前确认过"变得可查询,产品侧可以在(比如)一年后主动提示"要不要重新做一次体质测试"——这是比"自动漂移"更安全、也更符合中医体质相对稳定这一前提的设计。

**4. 体质未知/未确认时,TCM SubAgent 的降级行为需要显式定义,不能悬空。** 如果用户选择跳过体质获取,`完整推荐`/`候选评估`等需要 TCM 判断的分支不能报错,也不能悄悄套用一个默认体质(套用错误体质比"不知道"更危险——相当于给用户扣错体质的帽子,可能导致方向性错误的调理建议)。**降级规则**:`constitution` 为空时,TCM SubAgent 的任务提示词里显式声明"体质未知",建议范围收窄为体质无关的普适性温和建议(比如"少辛辣油腻、规律饮食"这类不依赖具体体质分型的通用原则),并在回答末尾附一句引导("完善体质信息后可以给出更精准的建议"),不阻塞对话继续。这条规则补进 §5.2 步骤 3 的 TCM SubAgent 任务描述里。

**放弃**:
- 强制注册时问卷,不答完不能用——和产品的对话式定位冲突,且拦住"只想问一个事实性问题"的轻量使用场景,违反 D17/D21 一贯的"不为了完整性牺牲最小可用路径"的立场
- 体质字段维持单值 `TEXT`,多个达标体质里只取分数最高的一个——中医"体质夹杂"是常见且有临床意义的信息,丢弃次要体质会让 TCM SubAgent 拿到的信息比实际问卷结果更贫乏,属于不必要的信息损失
- 舌象照片识别作为体质获取的补充路径——D5 已经排除,理由不变(准确性在本项目范围内不可验证),这次细化不重新打开这个选项

**理由**:方法论上与 D25/D27 一致——先枚举"用户可能已知/不可能已知体质"这两条真实路径,再倒推数据模型该长什么样,而不是先定字段再削足适履。`constitution_source`/`constitution_confirmed_at` 的设计直接来自 D27 里"Advanced JSON Cards 需要携带来源和时间戳,而不只是携带值"这条调研结论——这是本次几点请求之间少见的一处直接互相支撑的例子:记忆架构调研的结论,具体落到了体质字段设计上。

**面试要点**:体质夹杂(多体质同时达标)这个细节容易被忽略,是因为大多数人对"问卷计分"的默认想象是"选一个得分最高的",但这不符合 CCMQ 量表本身的设计意图和中医临床实践——愿意为这类"看起来是工程细节、实际是需要懂业务背景才能发现"的问题绕一圈,是能体现"不是纯技术背景硬套 TCM 项目"的一个具体例子。

## D29 · LLM adapter 支持多 provider(细化 D19)

**背景**:2026-08-26,`backend/llm/adapter.py`(D19 双档策略的落地)最初只支持 OpenAI 兼容的 chat completions 格式。实现完之后用户提出:本机同时装了 Ollama(本地免费跑模型)和 Anthropic API key,希望 dev/prod 两档能各自选用不同的服务商,而不是被锁死在"OpenAI 兼容端点"这一种形态。

**选择**:

**1. 拆出 Provider 抽象层,adapter.py 本身与具体服务商解耦。** `backend/llm/providers/base.py` 定义一个只有三个方法的协议:`call(messages, model, **kwargs)`(发起调用,返回归一化的 `ProviderResponse`)、`classify_error(exc)`(把该服务商 SDK 的异常归类成 `retryable`/`non_retryable`)、`aclose()`。adapter.py 里的重试/退避/熔断循环只认这个协议,不知道也不关心背后是谁——新增一家服务商只需要实现这三个方法,不用碰重试/熔断的核心逻辑。

**2. OpenAI 和 Ollama 共用同一个 Provider 实现,不单独为 Ollama 写代码。** Ollama 从某个版本起自带 OpenAI 兼容层(`http://localhost:11434/v1`),请求/响应格式和 OpenAI 本身完全一致,区别只在 `base_url` 和要不要真实 `api_key`(Ollama 不校验,但 SDK 要求非空字符串)。`OpenAICompatibleProvider` 这一个类同时覆盖 OpenAI、Ollama、以及任何其他声称"OpenAI 兼容"的服务商,不为了"看起来支持了 Ollama"就重复实现一遍相同的调用逻辑。

**3. Anthropic 必须单独实现,不能套用同一个类。** Anthropic 的 Messages API 和 OpenAI 的 chat completions 格式**不兼容**:system prompt 是顶层独立参数而不是 messages 列表里的一条;`max_tokens` 是必填参数(OpenAI 可以不传);响应是 content blocks 列表而不是单一字符串;停止原因的字段名和取值都不同,且**没有**和 OpenAI `content_filter` 完全对应的值。`AnthropicProvider` 单独做这几处格式翻译,并在代码注释里如实标注"内容策略拒绝检测在 Anthropic 这边不对等"这个已知差异,不假装两边完全一致。

**4. dev/prod 两档可以是不同服务商,不只是同一服务商的不同模型。** 新增 `LLM_PROVIDER_DEV`/`LLM_PROVIDER_PROD` 环境变量(不设就退到通用的 `LLM_PROVIDER`,再不设默认 `openai`,保持对此前行为的向后兼容)。这是本次改动的核心价值:比如 dev 档指向本地 Ollama(免费、无需网络,适合高频迭代),prod 档指向 Anthropic/OpenAI(真实交付质量)——D19 原本的"双档"只区分了"贵/便宜",没有考虑到"本地/云端"这另一个独立维度,这次一并解决。

**5. Ollama 不给内置默认模型,显式报错而不是瞎猜。** OpenAI/Anthropic 各自有稳定的公开模型名可以当默认值(比如 `gpt-4o-mini`、`claude-haiku-4-5-20251001`);Ollama 则完全取决于这台机器 `ollama pull` 过什么,猜一个默认值大概率指向一个没被拉取过的模型名,报错反而更有帮助。`LLM_MODEL_DEV`/`LLM_MODEL_PROD` 未设置且 provider 是 ollama 时,直接抛出说明性错误,不是静默失败或用一个可能不存在的模型名去调用。

**放弃**:
- 为每个服务商单独维护一套完整的重试/熔断实现——会导致同一段可靠性逻辑(ENGINEERING §1)散落在三个文件里,以后改退避策略要同步改三处
- 给 Ollama 单独写一个 Provider 类——它的请求/响应格式和 OpenAI 完全相同,单独实现是纯粹的重复劳动
- 把"provider 选择"做成运行时可由模型/agent 自主判断的东西——这仍然是纯配置驱动的环境变量,不是 D20 定义的五处 agent 行为之一,选哪个服务商是部署时的运维决策,不是推理时的智能决策

**理由**:方法论与 D19 一致——双档策略要解决的是"开发迭代成本 vs 交付质量"这个矛盾,而"本地免费模型 vs 云端付费模型"是这个矛盾在部署形态上的具体体现,细化 D19 而不是另开一条决策。Provider 抽象的收益是"以后要接第四家服务商(比如文心一言/通义千问的原生 API)只用加一个新文件,不用动 adapter.py 已经测过的重试/熔断逻辑"。

## D30 · `user_profile` 新增 `city`/`timezone` 字段;`query_diet_log` 新增 `by_meal_type` 聚合

**背景**:实现 `query_diet_log`(阶段4任务3)时,相对日期解析("今天"/"昨天")的时区基准是"待决问题"表里挂了很久的一条——`user_profile` 一直没有城市/时区字段,只能先用 `DIET_EXPERT_TZ` 环境变量兜底。2026-08-26 用户明确要求解决这个问题,并指出 `city` 字段对 `query_weather` 同样重要(不用每次对话都问用户在哪),顺带批准把此前出于"不在当前工具签名范围内"被撤回的 `by_meal_type` 聚合正式加回去。

**选择**:

**1. `user_profile` 新增 `city TEXT` 和 `timezone TEXT` 两个独立字段,不做"从 city 反查 timezone"的地理编码。** 两个字段各自服务不同消费者:`city` 是给 `query_weather` 的 `city` 参数直接用的;`timezone` 是给相对日期解析用的权威依据。**不自动从 city 推导 timezone**——地理编码在行政区划时区边界、跨时区大城市(比如同名地名分属不同时区)、夏令时规则这些地方容易出静默错误,而 V1 用户量小,首次引导(§11)对话里直接问一遍、显式确认,比构建一套地理编码再让用户事后发现"怎么算出来的时间不对"更可靠,呼应 PRD §10.2 人在环原则一贯的取舍(宁可多问一句,不做看不见的自动推断)。

**2. 时区解析三层兜底优先级:`user_profile.timezone` > `DIET_EXPERT_TZ` 环境变量 > 硬编码 `Asia/Shanghai`。** 任何一层缺失或者值不是合法 IANA 时区名(比如画像字段手滑存错)都跳过、退到下一层,不因为某一层数据有问题就让整个工具报错——查时区是为了给"今天是哪天"这类判断兜底,兜底逻辑本身不应该成为新的单点故障。环境变量这一层保留下来,不是因为它还需要独立存在,而是本地开发/测试时不想每次都建一条 `user_profile` 记录才能跑通,属于开发期便利,不是长期的时区来源。

**3. `by_meal_type` 聚合补回 `query_diet_log`。** `diet_log` 表本身已经有 `meal_type` 字段(早餐/午餐/晚餐/夜宵/下午茶/加餐/未知),之前在阶段4任务3的实现里被主动撤回过一次——理由是当时 ARCHITECTURE §2.2 的工具签名只列了 `by_ingredient`/`by_property`/`by_nutrient`/`raw` 四个,擅自多加一个聚合维度属于没有跟设计对齐就扩展接口。这次是先改了 ARCHITECTURE.md 的工具签名、再回来实现,不是反过来——"改没改设计"这个先后顺序被保留下来了,不是"用户说加就直接加代码"。加了之后 `backend/mcp_server/registry.py` 的 `aggregation` 枚举也同步更新,两处不能只改一处。

**放弃**:
- 从 `city` 字符串自动反查 `timezone`(比如接入某个地理编码/时区数据库)——V1 阶段引入这类第三方数据依赖,收益(省用户填一个字段)配不上风险(时区算错导致"今天"算错、进而影响过敏原核查之外的所有相对日期判断),且违反 D21"不做沙盒/代码执行"同一精神下"不为了自动化引入不必要的外部依赖"
- 给 `city`/`timezone` 也套用 D28 体质字段那套"主/次/来源/确认时间"结构——体质有"体质夹杂"这种真实存在的多值场景,城市/时区是单值属性,没有对应的复杂度,套用同一结构是不必要的过度设计

**理由**:这条决策是"待决问题"表机制本身价值的一个具体例子——时区基准这个问题从"实现 query_diet_log 时先把坑点记下来"到"真的有了字段去解决"之间隔了一次对话,期间没有被遗忘或者被绕过去搪塞,而是等到有真实需求(用户点名要解决)时按记录下来的坑点直接处理,没有重新发明一遍分析过程。

## D32 · 一句话包含多个意图时的多任务路由(细化 D12/D25)

**背景**:D12/D25 定下的六分支路由隐含"一条消息一个分支"的假设。真实验证时发现,像"帮我记录一下中午吃了麻婆豆腐,另外阳虚质应该吃什么"这种一句话夹带两个独立意图的输入,`classify_route` 按固定优先级只会命中排在最前面的"记录"分支,整条原文喂给记录分支的处理逻辑,"阳虚质应该吃什么"这半句话不会被路由到任何地方,直接消失——用户只会收到记录确认,完全没意识到自己的第二个问题没人回答。

**选择**:加一层确定性的"意图连接词"切分(另外/顺便/还有/再问一下等,**中英双语**——六分支路由本身每条分支的正则都是中英双语的,`_LOG_WRITE`/`_SINGLE_DOMAIN_TCM` 等列表里既有中文子串匹配也有 `_en()` 包的英文模式,连接词切分不该只认中文),对每个切出来的片段独立跑既有的 `classify_route()`,只有**每个片段都规则命中**且**至少两个片段分支不同**时才判定为多任务、逐个顺序分发;不满足就整条消息按切分前的单分支路径处理,行为和这条决策生效前完全一致。SSE 协议新增 `task`/`task_done` 两个事件包住每个子任务的既有事件序列,整个轮次只有最后一条真正的 `done`。完整设计见 `ARCHITECTURE.md` §5.1.1。

**放弃**:用 LLM 做语义切分——那样能识别没有连接词的隐式多意图(比如"麻婆豆腐好吃吗我中午吃了"这种糅在一个从句里的说法),但意味着每条消息(哪怕只有一个意图)都要多一次分类调用的延迟和成本,和 D12"V1 用确定性规则路由,不调 LLM"的既有原则冲突。确定性连接词切分会漏掉隐式多意图,这是刻意接受的取舍,不是没想到。

**理由**:和 D25 的方法论一致——先枚举真实会出现的输入形态(单意图 vs 显式多意图 vs 隐式多意图),再决定要不要为某一类单独处理,而不是笼统地上一个"更聪明"的方案。显式连接词切分覆盖了"用户明确用另外/顺便这类词开启第二个话题"这一类最常见、代价最小的场景,隐式糅合的场景发生率更低、且用规则做几乎不可能不误判,留给以后有真实数据支撑再考虑要不要上语义方案。

**面试要点**:这条决策展示了"先证明保守方案在真实场景里够用,再决定要不要上更贵的方案"这个思路——多任务路由完全可以一步到位上 LLM 语义切分,但那样会让"V1 路由不调 LLM"这条已经论证过的决策打折扣;用连接词切分 + "全部片段都必须规则命中"这个保守到近乎苛刻的激活条件,把误判率压到接近于零(宁可漏检,不误拆一句其实是单意图的话),是工程上"先用最小代价覆盖大多数真实场景"的一个具体例子。

**补充(2026-08-27,用户明确要求补 LLM 兜底)**:纯规则切分会漏掉两类情况——①连接词存在但某个片段规则没命中(比如"...另外我今天心情不好"，"心情不好"不落在任何一条分支正则里)；②压根没用连接词的隐式多意图(比如"麻婆豆腐好吃吗我中午吃了")。新增 `classify_turn()` 取代 `api/main.py` 原来"先调 `classify_multi_task()` 再调 `classify_route_async()`"两段独立调用，合并成一次决策：规则能确定就不打LLM(零成本场景不变)，规则完全没命中、或者有连接词但没法确认属于哪种情况时，打一次 LLM 请它直接判断"这句话该拆成几个任务"(`{"tasks":[...]}`，长度可以是1)。**这不是推翻"放弃"那一节的立场，是把"隐式多意图"这个原本"发生率低、暂不处理"的取舍，按用户的明确要求提前实现**——触发条件依然保守(连接词同分支的情况仍然不触发)，不是对每条消息都打LLM。

真实验证时发现一个这次仍然覆盖不到的情况，如实记录：如果整条组合消息**没有连接词**、但**恰好**被某条分支正则在不该匹配的位置命中(比如`"我想知道气虚质应该怎么调理饮食，我昨天都吃了什么给我查一下"`——`_LOG_REVIEW`正则"我.{0,8}(昨天|...).{0,12}吃了什么"在整句里搜到子串，`rule_matched=True`)，`classify_turn()`会直接采信这个"confidently"但其实不完整的规则结果，前半句照样丢失，LLM复核根本不会被触发。要补这个洞需要放弃"只在规则拿不准时才打LLM"，改成对每条消息都做一次LLM复核——是否要付这个成本，留给以后再决定。

## D33 · 新增 OTHER 第七分支 + 统一"人在环追问"机制(落实 D20 #3、PRD §17)

**选择**:
1. 新增 `RouteBranch.OTHER` 第七分支——确定性锚定匹配(`_OTHER_GREETINGS`，整句 `^...$`，不是其余分支惯用的子串搜索，避免"谢谢你的建议，那我该吃什么"被误判)覆盖问候/致谢/告别；LLM 兜底(`classify_turn`)七选一里新增 `other` 描述覆盖其余情况。命中后 `_stream_other()` 一次 `complete()` 直接回应，**不经过 SubAgent、不经过核查**——闲聊按友好简短回应处理；食物相关但检索范围外的问题(比如具体烹饪做法)用通用知识回答但必须显式声明"这是通用知识，未经知识库验证"；完全无关的问题礼貌拒绝并引导回饮食话题。
2. 新增统一的"人在环追问"机制：`backend/agents/clarification.py`(`PendingClarification`/`ClarificationStore`/`InMemoryClarificationStore`，仿 `backend/onboarding/session_store.py` 的既有形状，key 用 `session_id` 而非 `user_id`——追问是"这次对话里正在问的一个具体问题"，不是全局一次性状态)；SubAgent system prompt 新增约定(`citation.py` `build_clarification_instruction()`)：判断对象本身指代不明时严格以 `[NEED_CLARIFICATION]` 开头回复；`api/main.py` 在 `_stream_log_write`/`_stream_single_domain`/`_stream_dual_dispatch`(覆盖 log_write + fact_query + single_domain + candidate_eval + full_recommend 共五个分支)进入核查/调和前检查这个标记，命中则存入 `ClarificationStore` 并吐 `clarification` SSE 事件；下一轮消息若有 pending 记录，`_stream_chat_inner` 直接拼接原文重新分发到当初的分支，不重新走路由。`allow_clarification` 参数贯穿全链路保证 PRD §11"追问一次，仍模糊则记为 unspecified"的单次上限——`clear()` 在重新分发前就调用，不管这次结果如何都不会问第三次。

**放弃**:
- 用户最初设想的"router LLM 自己 plan 怎么回答，设计一个 workflow 然后 step 到 step 完成"——排查后发现这类需求已经完全被 D20 已批准但未实现的五处 agent 行为点覆盖(OTHER 分支的判断本身就是路由级"不确定的是什么"，追问是#3 原文场景)，不需要在这五处之外再造一套新的动态控制流位置，那会违反 D20"动态控制流只出现在五个明确列举的位置"这条约束本身。
- 追问机制只覆盖 log_write：用户明确要求"一并把 candidate_eval 也做了"，因此选择在 SubAgent 层(system prompt 约定 + `citation.py` 标记)做一套通用机制,而不是限定在 log_write 一处用临时判断。

**真实验证踩过的坑(2026-08-27，本地真实 Postgres + 真实 Anthropic Haiku)**:
1. `build_clarification_instruction()` 最初的措辞("缺少判断所需的关键信息")范围太宽——"红烧肉能不能吃"这种已经点名具体菜品的问题，模型仍然会因为"没说明血脂血糖情况、没说明用糖腌制与否"这类外围细节触发反问，等同于对每个候选评估都追问一轮。收窄成"只在判断对象本身是谁/是什么都不确定时才触发，外围细节按用户画像+常规假设兜底"后修复——这是 PRD §11"输入模糊"真正想覆盖的场景(指代不明，不是信息不够全面)，过宽的约定等于把"追问一次"的克制原则变成"逢事必问"。
2. `_dispatch_branch()` 对 `RouteBranch.OTHER` 的检查顺序放在了 `LOG_REVIEW` 之前——纯粹的分支路由代码问题，写测试时才发现顺序不影响正确性(各分支互斥)，记录是因为最初担心过顺序会不会影响 `_stream_multi_task` 的多任务场景，验证后确认不会。
3. 真实验证 candidate_eval 两轮追问流程时，追问→补充→重新分发到 SubAgent 这一段行为正确(两侧 SubAgent 都给出了真实结论，TCM 侧真的调用了 `retrieve_tcm`)，但调和层(`reconcile_subagent_results`，D19"永远 `force_prod_tier=True`")在本地环境因为没配置 prod 档 LLM 凭据而失败——这是本地开发环境的既有限制(D19 生效以来就存在，`.env` 只配了 `LLM_PROVIDER_DEV`/`LLM_MODEL_DEV`)，不是这条决策引入的新问题，如实记录以免误判成本次改动的回归。

**理由**:两个需求排查后都不是"缺新架构"，而是"已经批准的设计从未落地"——按 ENGINEERING 的一贯原则，先看现有决策文档里是否已经覆盖，而不是遇到空白就默认要发明新机制。

## D36 · 撤销 dish_decomposition 的连接词短路优化(真实数据发现漏记)

**背景**:`decompose_meal()` 命中全局菜品表之后,原本靠一份连接词关键词表("加"/"和"/"还有"/"跟"/"以及"...)判断剩余文本里是不是还提到了别的东西——这个设计本身是为了避免"帮我记录一下，中午吃了麻婆豆腐"这类纯叙述性填充词每次都多打一次 LLM。2026-08-30 给真实用户(`u_624f74a601e8`)补录历史饮食记录时发现：这个关键词表覆盖不了用户实际的分隔习惯——"鸡爪+牛肉南瓜炖年糕+半个小西瓜"用"+"分隔多个菜品，"+"不在关键词表里，命中全局表的"南瓜"/"西瓜"两个子串之后直接短路，"鸡爪"和"牛肉南瓜炖年糕"整条丢失，且这类关键词表本质上永远会有覆盖不到的分隔方式(换行、"/"、纯空格...)，不是加几个词就能穷举完的。

**选择**:去掉连接词关键词表这一层判断——全局表匹配完之后，只要还有非空残留文本(`normalize_phrase()` 判断)，就无条件继续走"个人别名→LLM 兜底"，把"要不要认为残留文本里还有别的食物"这个判断完全交给 LLM 自己做，不再用一份关键词表去猜。已修正的历史数据(该用户 8/30 晚餐那条记录)见对话记录。

**放弃**:
- 只是把"+"/"、"等符号加进关键词表——本质上还是关键词表，用户总会用到表里没预料到的分隔方式，治标不治本。
- 保留关键词短路优化：这条优化本身是有真实代价依据的(见下面"代价")，撤销它不是没考虑后果，是明确选择"宁可多花一点 LLM 调用，也不要漏记"。

**代价(如实记录)**:这条优化最初就是为了解决"早先实现对任何非空残留都退回 LLM，导致几乎每条 log_write 消息都要多打一次"这个问题才加的(见 `dish_decomposition.py` 里 2026-08-27 前后的测试历史)。撤销之后，这个成本问题原样换回来了——任何"全局表命中 + 有残留叙述性文字"的消息，现在都会多打一次 LLM(该次调用会正确返回空 `dishes`，不会插入错误菜品，只是有延迟/成本)。

**理由**:两个方向都不完美，是在"确定性成本更低但会漏记"和"LLM成本更高但不会漏记"之间的取舍；这次是被真实丢数据的案例触发重新评估，用户明确选择了"宁可多花一点，不要漏记"这一侧。

## D37 · 核查全部拒绝时补一条诚实的兜底提示(不再是空气泡)

**背景**：真实生产 trace 发现一次完整跑完(11次LLM调用、约5分钱)但被 `verify()` 全部拒绝的请求(根因：Nutrition SubAgent 没有检索任何资料就写了一段带犹豫口吻的"结论"，既没有走 `[NEED_CLARIFICATION]` 正式协议，也没按 prompt 要求给出基于合理假设的答案；调和层把这段无引用内容揉进最终回答，核查按 PRD §10.1"无 source_id → 移除，不补全"把整段拒了)。`backend/agents/dispatch.py` 原有行为是拒绝后只吐 `guardrail`(机器可读的 `reason` 字符串)+`done`，不吐任何 `token`——前端目前只把 `guardrail` 渲染成小标签，不当正文展示，用户看到的实际上是一个空聊天气泡，和系统故障没有视觉区别。用户反馈"老是什么都被拦截了，没有任何输出"。

**选择**：`_stream_verification_result()` 全部拒绝分支新增一条静态、不含任何未核查内容的诚实兜底提示文本(`_VERIFICATION_REJECTED_FALLBACK_MESSAGE`)，作为 `token` 事件吐出——明确告诉用户"没能给出有依据支持的具体建议"，并给出可执行的下一步(换个问法/补充细节)。被拒绝的原始内容(可能带幻觉引用、可能泄漏过敏原)本身依然绝不会被吐出来，这条提示是独立组装的静态文本，不依赖被拒绝的内容。过敏原重试仍上限1次；依据不足现在先走一次无工具证据修复，修复失败才使用这条静态兜底。

**放弃**：
- 放宽 PRD §10.1"无 source_id → 移除，不补全"这条初始硬检查本身(比如让模型"补全"一个引用)——修复调用只能保留内容并明确标注通用知识，不能制造 provenance；这次改动不碰过敏原/ED/诊断性硬防线。
- 把被拒绝的原始内容脱敏/摘要后展示给用户("虽然没通过核查，但大概意思是...")——这本质上还是把未经验证的内容传达给用户，只是加了一层免责声明，和"移除，不补全"的精神冲突。

**理由**：模块文档原有的"重试一次不够就老实拒绝，比装作还有救更诚实"这条原则本身没有问题，问题是"老实拒绝"之前只做到了对日志诚实(机器可读的 `reason` 字符串)，没有做到对用户诚实(用户端是完全的空白，看起来像 bug 而不是一个经过深思熟虑的安全决定)。这条改动把"诚实"这个原则也落实到用户能看见的地方。

## D35 · 检索评分方法优化:混合检索(dense+sparse)+ MQE(落实 §2.6 触发条件)

**背景**:`ARCHITECTURE.md` §2.6 早就写了 MQE/HyDE 两个方向,但明确"没有 baseline 数字支撑,等 recall@5 数字稳定之后再考虑"。2026-08-30 `EVALUATION.md` §7.7 跑出生产检索(BGE-M3+pgvector)官方 context_recall=73.3%(刚过 Launch 70%,离 Target 85% 还差不少),四条没过的失败案例(`E1-01`/`E1-02`/`E1-06`/`E1-14`)有一致模式:查询里混了多个信息点(比如"平和质的人在春天饮食上要注意什么"同时有体质+季节两个信息点),且这两个信息点之间往往没有任何标点/连接词分隔,单一向量检索被其中一个信息点主导,另一个被挤掉。§2.6 原文设的"等待条件"(有真实失败案例证据,不是凭直觉)已经满足。另外发现 `RetrievedChunk.score` 字段算出来之后没有任何地方使用(不做阈值判断,也没告诉过 SubAgent 这个数字是什么),等于白算。

**选择**:
1. **混合检索(dense+sparse)默认开**:BGE-M3 一次 `model.encode()` 本来就能顺带产出稠密向量和词法(sparse)权重两路输出,之前只存了前者。新增 `sparse_embedding sparsevec(250002)` 列(维度=BGE-M3 底层 XLM-R tokenizer 实测 vocab_size,不是猜的),两路各自在 Postgres 里排序取候选池,用 Reciprocal Rank Fusion(RRF,k=60 业界惯用常数)融合成最终排名——两路原始分数量纲不同(cosine 相似度 vs 词法内积),融合排名比融合分数更稳妥,不需要给两路分数找一个共同的校准方式。
2. **MQE 默认开(`retrieve_tcm`/`retrieve_nutrition`)**:用一次轻量 LLM 调用把 query 拆解成最多 2 个不同角度的改写版本,每个版本各自跑一遍上面这套混合检索,所有版本的结果一起参与最终 RRF 融合。这是"检索工具实现内部的增强"(§2.6 原文用词),不是新增一个 agent 决策点——`use_mqe`/`use_hybrid`/`complete` 三个参数不在 MCP 工具的 JSON Schema 里,SubAgent 完全不知道这一层存在。
3. **`RetrievedChunk.score` 语义调整为"最高原始相似度",而不是 RRF 分数本身**——RRF 分数只有相对大小意义,不适合直接暴露给 SubAgent 做"这条资料靠不靠谱"的判断;融合之后返回的 `score` 是该 chunk 在所有参与融合的列表里出现过的最高原始 cosine/inner-product 值,保留"越接近1越相关"这个直观含义。
4. **补上 score 的使用指引**:`backend/agents/citation.py` 新增 `build_score_guidance_instruction()`,拼进两个 SubAgent(以及 B2 ablation baseline)的 system prompt,告诉模型这个字段是什么、以及"这次检索结果整体 score 偏低时应该如实说明知识库没有直接覆盖,而不是牵强引用凑一个结论"。刻意不在后端按阈值静默丢弃低分 chunk——那样模型完全看不到"知识库其实没有强相关资料"这个信号,反而更容易在信息不足时硬凑答案,和 D15"只拒绝不改写"的精神相反：宁可让模型自己看到弱证据然后诚实声明信息不足,也不要后端替它做隐性过滤决定。

**放弃**:
- **HyDE**:两个方向不是非此即彼,MQE 已经覆盖了当前观察到的失败模式,HyDE 要解决的问题目前没有专门的失败案例证据支撑它比 MQE 更优先,继续按 §2.6 原有方法论,等后续 eval 需要时再评估,不是这次一次性两个都做。
- **纯规则式(标点/连接词/预定义体质+季节词表)拆分 query,不引入 LLM 调用**:失败案例的真实查询文本(比如"气虚质春季容易疲乏，饮食上怎么补？")里,体质和季节两个信息点经常完全没有逗号或连接词分隔,融在同一个短语里,规则式拆分大概率救不回这几条已知失败案例；即便用预定义的体质/季节词表做关键词抽取,也只是针对这一类失败的打补丁,不能泛化到其他类型的多信息点查询(比如 `E1-14`"补铁的时候能喝茶吗"根本不涉及体质/季节)。用户在这两个方向之间被问过一次,明确选择了 LLM 改写。
- **在同步的 `search_knowledge_chunks()` 内部把 MCP 协议层/Agent Loop 整体改成 async 来"干净地"支持 MQE 的 LLM 调用**:牵动全部六个工具 handler 的签名和 `backend/mcp_server/server.py`/`backend/agents/agent_loop.py` 的调用约定,风险和收益不成比例。改用 `_run_coroutine_sync()`——检测调用栈是否已经身处一个运行中的 event loop(比如 `run_agent_loop()` 内部),是则在独立线程里起一份全新的 event loop 跑这个协程,否则直接 `asyncio.run()`,把桥接完全封装在 `_retrieval_common.py` 内部,不改动其余任何函数签名。

**代价(如实记录,不是遗留问题)**:
1. MQE 默认开启后,`retrieve_tcm`/`retrieve_nutrition` 每次调用最多变成 3 个 query 变体 × (dense+sparse) = 最多 6 次候选检索 + 1 次 LLM 改写调用,延迟和成本比之前的单次 dense-only 检索明显增加。SubAgent 一次任务循环里可能多次调用检索工具(§5.4 上限 15 次),worst case 下检索本身占用的时间会显著增加。这是在"改进 recall"和"延迟/成本"之间的主动取舍,不是没考虑到。
2. **真实跑分发现的回归,不是理论上的担忧**：接入后重跑 `evals/run_vector_m1.py`(见 `EVALUATION.md` §7.7.3),官方 Recall@5(组平均)从 76.7% 掉到 73.3%,定位到 `E1-08`(「湿热质夏天饮食方向是什么？」)一题因为稀疏(词法)通道对关键词表面重合更敏感,把两条"体质定义性描述"(词面重合度高、内容更泛)排到了"具体饮食指导章节"(gold chunk)前面,挤出了 top-5。这次跑分同时撞上 dev 档免费模型限流导致 MQE 大半降级为不生效,所以现在还不能判断"MQE 真正生效后"综合效果是正是负——已决定不为了拿到这个数字继续消耗真实 prod 档 API 配额(2026-08-30),如实标注为待后续验证的已知限制,候选缓解方向记在 `EVALUATION.md` §7.7.3 末尾,不是这次顺手就能定论的事。

**理由**:§2.6 原文设的三条等待理由(没有 baseline 数字、成本代价、需要错误归因方法论)现在都有了对应的证据链——有真实的 73.3% baseline、有具体的 4 条失败案例归因、且选择的具体技术(MQE 而非 HyDE、混合检索而非纯 rerank)是基于这些失败案例的实际模式(多信息点缺失,不是专有名词完全查不到)而不是理论推演。
